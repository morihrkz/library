JAVASCRIPT / 10-DAY GUIDE

JavaScript ゼロからイチまで

HTML は書けるけど、 JavaScript は長年ナナメ読みしてきた人のための 10 日間

本稿の使い方

本稿は「 JavaScript ゼロからイチまで」というタイトルの通り、 JavaScript を完全にマスターする本ではない。 1 を 10 にするのではなく 0 を 1 にする本である。
あなたはこれまで長年、 HTML ファイルの中で <script> タグやコードの断片を何度も目にしてきたはずだ。おまじないのようにコピーして貼り付け、動けば良し、動かなければ別のコードを探す。そんな付き合い方を続けてきたのではないだろうか。
本稿の目標は、その「おまじない」を「自分の言葉で説明できるもの」に変えることである。

想定している進め方は「 1 日 1 章に取り組み、それを 10 日間続ける」というものである。全 10 章がちょうど 10 日分に対応していて、各章は「読む」パートと「実際に手を動かす」パートの両方を含んでいる。
一気に全部読み切る必要はない。むしろ、写経のように実際にファイルを作り、ブラウザで開いて、動く様子を自分の目で確認しながら進めることを強くすすめる。

前提として、あなたはすでに次の様な状態であるということを想定している。
「 HTML ファイルの仕組みを理解している」
「テキストエディタでコードを編集／保存できる」
「簡単なコマンドを実行できる」
「普段から AI のコーディング支援を使ってチャット形式で開発を進めている」
つまり、プログラミングには慣れているけれど JavaScript そのものは体系的に学んだことがないという状態である。
だから本稿では、変数や関数といった超基本の説明も省略しないが、逆に「 JavaScript のエンジンが内部でどう処理を最適化しているか」のような深い実装の話には立ち入らない。
あなたが本当に必要としているのは、目の前のコードが「何をしようとしているのか」を読み解ける力と、自分でも簡単なものなら書ける力だからである。

JavaScript はどこで生きている言語か

JavaScript は、もともと Web ブラウザの中で HTML ページに動きを与えるために作られたプログラミング言語である。 HTML が「ページの構造 ( 見出しはここ、段落はここ ) 」を決め、 CSS が「見た目 ( 色やレイアウト ) 」を決めるのに対して、 JavaScript は「振る舞い ( クリックしたら何が起きるか、入力値に応じて何が変わるか ) 」を担当する。
よく「 HTML は骨格、 CSS は服装、 JavaScript は筋肉や神経」というたとえ方をされるが、感覚としては近いだろう。

今では JavaScript はブラウザの中だけの言語ではなくなった。
Node.js という仕組みを使えば、サーバー側のプログラムやコマンドラインツールも JavaScript で書ける。本稿では主にブラウザの中で動く JavaScript 、つまり皆さんが普段目にしている HTML ファイルの中のコードを中心に扱うが、覚えた文法や考え方の多くはサーバー側の JavaScript にもそのまま通用する。

コラム ( 事実 ): なぜ 10 日間で作られた、と言われるのか

JavaScript は 1995 年、 Netscape 社の Brendan Eich( ブレンダン・アイク ) という技術者によって作られた。 Eich 本人が自身のブログで振り返っているところによれば、当初「 Mocha 」という名前で試作されたプロトタイプは、 1995 年 5 月のごく短い期間で作られたとされている 1 。
この逸話は「たった 10 日間で 1 つの言語が生まれた」という劇的なストーリーとしてしばしば語られるが、その後 Netscape がブラウザへの実装や仕様の細部を詰めるのにはさらに長い時間をかけている。つまり「 10 日間で完成品ができた」というより「 10 日間で最初の動く試作品ができた」と捉えるほうが実態に近い、という指摘もある 2 。

名前についても紆余曲折がある。最初は「 Mocha 」、ベータ版では「 LiveScript 」と呼ばれていたが、 1995 年 12 月、 Netscape と Sun Microsystems( 当時人気のあった Java 言語を開発していた会社 ) の提携にあわせて「 JavaScript 」という名前に変更された 3 。
ただし JavaScript は Java を土台にした言語ではなく、文法の一部が似ている程度で、設計思想はかなり異なる。「名前は似ているけれど別物」という点は、この先ずっと覚えておいて損はない。

JavaScript を動かす 3 つの方法

JavaScript のコードを実際に動かす方法は、大きく分けて 3 つある。どれも今日から試せるので、実際に手元でやってみよう。

方法 1: ブラウザの開発者ツールのコンソールに直接書く

Chrome ・ Edge ・ Firefox などのブラウザには「開発者ツール」という機能が組み込まれている。適当な Web ページを開いた状態でキーボードの F12 キー (Mac では Command+Option+I) を押すと、画面の一部に開発者ツールが表示される。
その中の「コンソール」というタブを開くと、 JavaScript のコードを 1 行ずつ試しに書いて実行できる場所が出てくる。ここに次のように打ち込んで Enter キーを押してみてほしい。

console.log("こんにちは、JavaScript");

コンソールに「こんにちは、 JavaScript 」という文字列が表示されれば成功である。 console.log() は、カッコの中に書いたものをコンソールに表示する命令で、本稿でも今後、動作確認のために何度も登場する。

方法 2:HTML ファイルに <script> タグで直接書く

HTML ファイルの中に、次のように <script> タグを置くと、その中に書いた JavaScript のコードがページの読み込み時に実行される。

<!DOCTYPE html>
<html lang="ja">
<head><meta charset="UTF-8"><title>サンプル</title></head>
<body>
  <h1>サンプルページ</h1>
  <script>
    alert("ページが読み込まれました");
  </script>
</body>
</html>

このファイルをブラウザで開くと、ページが表示されるタイミングでポップアップのアラートが出るはずだ。 alert() はブラウザに強制的にポップアップを出す命令で、動作確認には便利だが、実際の Web サイトで多用すると使い勝手が悪いため、この記事では以後あまり登場しない。

方法 3: 外部の .js ファイルとして分離して読み込む

実務でもっともよく使われるのがこの方法である。 HTML とは別に拡張子 .js のファイルを作り、それを <script> タグの src 属性で読み込む。

<!-- index.html -->
<script src="main.js"></script>

// main.js
console.log("外部ファイルから実行されました");

HTML と CSS を別ファイルに分けるのと同じ発想で、 JavaScript も別ファイルに分けておくと、コードの見通しがよくなり、複数の HTML ページから同じ .js ファイルを使い回すこともできる。
<script> タグを置く位置は、歴史的には </body> の直前 ( ページの中身を先に表示してから読み込む ) がよく使われてきたが、 defer 属性を使う書き方 (<script src="main.js" defer></script>) も広く使われている。これは「どちらが絶対的に正しい」という話ではなく、ページの構成やパフォーマンス方針によって選び方が変わる部分である。
この記事では以降のサンプルコードを、断りがない限り外部ファイル読み込みを前提に記述する。

アドバイス ( 筆者の見解 )

普段から AI のコーディング支援を使っている方に向けて、本稿での付き合い方を 1 つ提案する。本稿を読みながら「このコード、 AI に聞けば一瞬で書いてくれるのでは」と思う場面が何度もあるはずだ。それは事実その通りである。
ただし、本稿の目的は「 AI が書いたコードを読んで、何が起きているか自分の言葉で説明できるようになること」である。手を動かすパートでは、まず AI に頼らず自分で書いてみて、動かなかったときに初めて AI に「なぜ動かないか」を聞く、という順番を試してみてほしい。答え合わせに AI を使うのは効果的だが、最初の一手まで委ねてしまうと、本稿を読む意味が半減してしまう。

今日の実習

次の 3 つを実際にやってみよう。
(1) 適当な Web ページを開き、開発者ツールのコンソールで console.log() を試す。 (2)<script> タグを直接埋め込んだ HTML ファイルを 1 つ作り、ブラウザで開く。 (3)HTML と .js ファイルを分けた構成を作り、外部ファイルとして読み込む。
3 つとも「画面に何かが表示された / 起きた」ことを目で確認できたら、 1 日目は達成である。

変数とは、名前のついた入れ物

プログラムは基本的に「値を覚えておいて、あとで使う」ことの繰り返しである。この「値を覚えておく場所」に名前をつけたものが変数である。
JavaScript で変数を作るには let または const というキーワードを使う。

let userName = "田中";
const siteTitle = "サンプルサイト";

userName = "佐藤"; // letは後から書き換えられる
// siteTitle = "別の名前"; // constはこれをするとエラーになる

let は「後で値を変える可能性がある変数」、 const は「一度決めたら変えない変数」に使う。
迷ったときは、まず const で書いてみて、どうしても値を書き換える必要が出てきたときだけ let に変える、という進め方がよく勧められる。ただしこれは絶対のルールではなく、チームやプロジェクトの方針によっては最初から用途に応じて使い分ける流儀もある。

コラム ( 事実 ):var という古い書き方

古い JavaScript のコードや Web 上の記事では、 let や const の代わりに var というキーワードで変数を宣言しているものによく出会う。 let と const は 2015 年に標準化された仕様 ( 通称 ES2015 、 ECMAScript 2015) で追加されたもので、それ以前は var しか存在しなかった 1 。
var は挙動に癖があり ( たとえば { } のブロックの中で宣言しても外から参照できてしまう ) 、現在新しく書くコードでは let ・ const を使うのが主流である。ただし 20 年以上蓄積されてきた既存のコードは今も var のままのものが大量にあるため、読めるようにはしておく必要がある。

JavaScript の主なデータ型

変数に入れる値には「型」がある。 JavaScript でよく使う基本的な型は次の通りである。

型意味書き方の例
文字列 (string) テキストデータ "こんにちは"
数値 (number) 整数も小数も区別なく扱う 42, 3.14
真偽値 (boolean) 真か偽かの 2 択 true, false
undefined まだ値が代入されていない状態 let x; のときの x
null 「値が空である」と意図的に示す状態 let x = null;

undefined と null はどちらも「値がない」ことを表すが、ニュアンスが違う。 undefined は「まだ何も入れていない、宣言しただけ」という自然な状態で、 null は「意図的に空にした」ことをプログラマーが明示する値である。
この使い分けはチームやコードベースによって流儀が分かれる部分でもある。

コラム ( 事実 ):typeof null が "object" になる有名な癖

ブラウザのコンソールで typeof null と打つと、直感に反して "object" という結果が返ってくる。これは JavaScript 最初期の実装上、値の型を内部的に管理する仕組みに由来する既知の癖で、後から修正しようとすると世の中の大量の既存コードが壊れてしまうため、あえてそのまま残されていると説明されている 2 。
「言語の挙動は必ずしも直感通りとは限らない」ことを示す例として覚えておくとよいだろう。

文字列の中に変数を埋め込む : テンプレートリテラル

文字列と変数をつなげたいとき、バッククォート (`) で囲んで ${ } の中に変数を書く「テンプレートリテラル」という書き方が便利である。

const name = "田中";
const age = 34;

// 従来の書き方(文字列の連結)
console.log("私は" + name + "です。" + age + "歳です。");

// テンプレートリテラル
console.log(`私は${name}です。${age}歳です。`);

どちらも結果は同じだが、変数の数が増えるほどテンプレートリテラルの方が読みやすくなる。改行を含む長い文字列を書くときにも扱いやすいため、現在のコードではこちらが広く使われている。

複数の値をまとめる : 配列とオブジェクト

値が 1 つだけでなく複数まとまっている場合には、配列 (array) かオブジェクト (object) を使う。配列は「順番のあるリスト」、オブジェクトは「名前 ( キー ) と値のペアの集まり」である。

// 配列:順番のあるリスト
const fruits = ["りんご", "みかん", "ぶどう"];
console.log(fruits[0]); // "りんご"(先頭は0番目)

// オブジェクト:名前と値のペア
const user = {
  name: "田中",
  age: 34,
  isAdmin: false
};
console.log(user.name); // "田中"

HTML の構造を「入れ子になったタグの集まり」として捉えられるように、配列とオブジェクトも「入れ子」にできる。配列の中にオブジェクトを入れたり、オブジェクトの中の値として配列を入れたりすることも日常的に行われる。
この「入れ子にできる」という性質は、次の章以降で扱うデータ処理でも繰り返し登場する。

const で宣言しても、配列やオブジェクトの中身は変更できる

「 const は値を変えられない」と説明したが、これには少し補足が必要である。 const が禁止しているのは「変数に別の値を再代入すること」であって、配列やオブジェクトの中身そのものを書き換えることまでは禁止していない。

const fruits = ["りんご", "みかん"];
fruits.push("ぶどう"); // これはOK:配列の中身を追加している
console.log(fruits); // ["りんご", "みかん", "ぶどう"]

// fruits = ["別の配列"]; // これはNG:変数そのものへの再代入はエラーになる

const で宣言した fruits という「箱」自体を別の配列に差し替えることはできないが、箱の中に新しい果物を追加したり、既存の要素を書き換えたりすることはできる。この「箱を差し替えるのは NG 、箱の中身をいじるのは OK 」という区別は、配列やオブジェクトを扱い始めた学習者がつまずきやすいポイントの 1 つなので、頭の片隅に置いておいてほしい。

分割代入 : 必要な値だけを取り出す

オブジェクトや配列から特定の値だけを取り出して変数にしたいとき、いちいち user.name のように書かなくても済む「分割代入 ( デストラクチャリング ) 」という書き方がある。これも ES2015 で追加された機能である 3 。

const user = { name: "田中", age: 34, isAdmin: false };

// 従来の書き方
const name1 = user.name;
const age1 = user.age;

// 分割代入
const { name, age } = user;
console.log(name, age); // "田中" 34

オブジェクトが持つプロパティのうち、必要なものだけを同じ名前の変数として一気に取り出せるため、特にオブジェクトの一部分だけを使いたい場面でコードがすっきりする。配列に対しても同様の書き方 (const [first, second] = fruits;) ができる。

比較演算子 :2 つの値を比べる

「もし◯◯だったら△△する」という処理を書くには、まず 2 つの値を比べる方法が必要である。 JavaScript には次のような比較演算子がある。

5 > 3   // true(5は3より大きい)
5 < 3   // false
5 === 5 // true(等しい)
5 !== 3 // true(等しくない)

ここで注意したいのが、「等しいかどうか」を調べる演算子が ===( イコール 3 つ ) と ==( イコール 2 つ ) の 2 種類あることである。 == は型が違っても値を無理やり揃えてから比較する ( 型変換してから比較する ) のに対し、 === は型も含めて厳密に比較する。

"5" == 5   // true(文字列の"5"を数値5に変換してから比較する)
"5" === 5  // false(型が文字列と数値で違うので、等しくないと判定される)

この == の「よしなに変換してから比較する」という挙動は、慣れないうちは直感に反する結果を生みやすいため、実務では基本的に === ・ !== を使うことが広く推奨されている。ブラウザで実際に console.log("5" == 5) と console.log("5" === 5) を打ち比べてみると、この違いを体感できる。

if 文で処理を分岐させる

const score = 72;

if (score >= 80) {
  console.log("優");
} else if (score >= 60) {
  console.log("良");
} else {
  console.log("再テスト");
}

if の後ろの ( ) の中身が true になれば、続く { } の中の処理が実行される。 true にならなければ、 else if や else のブロックが順番に確認される。
HTML の入れ子構造に慣れている方であれば、 { } の対応関係を追う感覚はそれほど遠くないはずだ。

論理演算子 : 条件を組み合わせる

複数の条件を組み合わせたいときは、論理演算子を使う。

演算子意味例
&& 両方とも true なら true( かつ )age >= 18 && hasTicket
|| どちらかが true なら true( または )isAdmin || isOwner
!true/false を反転させる ( 否定 )!isLoggedIn

これらは if 文の条件だけでなく、単独でもよく使われる。特に && は「左側が true のときだけ右側を評価する」という性質を利用して、条件付きで処理を実行する簡易的な書き方としても使われる。

const isLoggedIn = true;
isLoggedIn && console.log("ログイン済みです");

true と false だけじゃない :truthy と falsy

JavaScript の if 文は、 ( ) の中身が必ずしも true/false そのものでなくても動く。
0 や空文字列 "" のような値も、 if 文の条件としては自動的に「 false のようなもの」として扱われるからである。この性質を「 falsy(false 的な値 ) 」、逆に「 true のように扱われる値」を「 truthy 」と呼ぶ。
falsy として扱われる値は、実質的に次の 6 種類だけである。

0
""(空文字列)
null
undefined
NaN(数値として不正な値)
false

これら以外の値 ( 文字数が 1 文字以上ある文字列、 0 以外の数値、中身が空でも配列やオブジェクトそのものなど ) は、すべて truthy として扱われる。

if ("") {
  console.log("表示されない"); // 空文字列はfalsyなので実行されない
}

if ("0") {
  console.log("表示される"); // 文字列としての"0"はtruthy(空文字列ではないため)
}

2 つ目の例のように、数値の 0 は falsy だが、文字列の "0" は truthy になる点は特に混同しやすいので注意してほしい。先ほど紹介した Null 合体演算子 ?? が生まれた背景には、まさにこの「 0 や "" のような、意図的に使われることもある値まで falsy 扱いで巻き込んでしまう」という || の性質への対応があった。

switch 文 : 同じ値による分岐が多いとき

if/else if が同じ変数の値だけを何度も比較する形になる場合、 switch 文を使うと意図が伝わりやすくなることがある。

const fruit = "みかん";

switch (fruit) {
  case "りんご":
    console.log("赤い果物です");
    break;
  case "みかん":
    console.log("オレンジ色の果物です");
    break;
  default:
    console.log("知らない果物です");
}

各 case の最後に break を書き忘れると、次の case の処理までそのまま実行され続けてしまう ( 「フォールスルー」と呼ばれる挙動 ) ため注意が必要である。 if/else if と switch のどちらを使うかは好みやチームの方針によるところが大きく、「同じ変数の値を複数の候補と比較する」場面では switch が、「複数の異なる条件を組み合わせる」場面では if/else if が選ばれやすい、という程度の目安で捉えておくとよいだろう。

三項演算子と、値が空かどうかを調べる新しい書き方

if/else を 1 行で書きたいときには、三項演算子 ( 条件 ? Aの場合の値 : Bの場合の値 ) がよく使われる。

const age = 20;
const message = age >= 20 ? "成人です" : "未成年です";

また、「値が null や undefined のときだけデフォルト値を使いたい」という場面のために、 Null 合体演算子 ?? という書き方もある。これは 2020 年に標準化された仕様 (ES2020) で追加された比較的新しい機能である 1 。

const nickname = null;
const displayName = nickname ?? "名無しさん";
console.log(displayName); // "名無しさん"

似た働きをする || との違いは、 || が 0 や空文字列 "" のような「 falsy だけれど意図的な値」までデフォルト値に置き換えてしまうのに対し、 ?? は null と undefined のときだけ反応する点である。たとえば得点が 0 点のユーザーの表示で score || "未回答" と書くと、 0 点も「未回答」に変換されてしまうため、こうした場面では ?? の方が意図に沿った挙動になる。

アドバイス ( 筆者の見解 )

=== と == のどちらを使うべきかは、 JavaScript 学習者の間で繰り返し話題になる論点である。
この記事では基本的に === を使う書き方で統一しているが、これは「 == が絶対に悪い」という意味ではない。意図的に型変換を利用したい場面ではあえて == を使う書き方も存在する。
ただし初学者のうちは、意図しない型変換によるバグを避けるために、まず === を基本にしておくことをおすすめする。

for 文 : 決まった回数だけ繰り返す

同じ処理を何度も繰り返したいとき、毎回コードを書き写すのは非効率である。 for 文を使うと、繰り返しの回数や条件を指定して同じ処理を自動で繰り返せる。

for (let i = 0; i < 5; i++) {
  console.log(`${i}回目です`);
}
// 0回目です 〜 4回目です まで、5回表示される

( ) の中は「開始時にすること (let i = 0) 」「繰り返しを続ける条件 (i < 5) 」「 1 回ごとに行うこと (i++ 、 i を 1 増やす ) 」の 3 つに分かれている。最初はとっつきにくく見えるかもしれないが、「 0 から始めて、 5 未満の間、 1 ずつ増やしながら繰り返す」と声に出して読んでみると構造がつかみやすくなる。

配列と組み合わせて使う for 文

配列の中身を 1 つずつ処理したいときは、配列の要素数 (length) を使って for 文を書くのが基本形である。

const fruits = ["りんご", "みかん", "ぶどう"];

for (let i = 0; i < fruits.length; i++) {
  console.log(fruits[i]);
}

配列専用の繰り返し :forEach ・ map ・ filter

配列の中身を 1 つずつ処理するだけなら、 for 文よりも簡潔に書ける専用の書き方がある。代表的なものが forEach ・ map ・ filter である。

const fruits = ["りんご", "みかん", "ぶどう"];

// forEach:1つずつ処理するだけ(戻り値はなし)
fruits.forEach((fruit) => {
  console.log(fruit);
});

// map:1つずつ加工して、新しい配列を作る
const upperFruits = fruits.map((fruit) => fruit.toUpperCase());
console.log(upperFruits); // ["RINGO"は入らない。もとの文字列を大文字化しただけの配列]

// filter:条件に合うものだけを残した新しい配列を作る
const longNameFruits = fruits.filter((fruit) => fruit.length >= 3);
console.log(longNameFruits); // ["りんご", "みかん", "ぶどう"] のうち文字数条件を満たすもの

forEach は「ただ順番に処理したいだけ」のとき、 map は「それぞれを加工した新しい配列がほしい」とき、 filter は「条件に合うものだけを絞り込んだ新しい配列がほしい」ときに使う、と覚えると使い分けやすくなる。共通しているのは、どれも ( ) の中に「配列の要素 1 つひとつに対して行いたい処理」を関数の形で渡している点である。
この「関数を値として渡す」という書き方は、次章で扱う関数の理解が深まると、より自然に読めるようになる。

for...of: 配列の中身を直接取り出す for 文

添字 (i) を経由せず、配列の中身を直接 1 つずつ取り出せる for...of という書き方もある。これも ES2015 で追加されたものである 1 。

const fruits = ["りんご", "みかん", "ぶどう"];

for (const fruit of fruits) {
  console.log(fruit);
}

fruits[i] のように添字を経由する必要がなく、 forEach と近い読みやすさを持ちながら、 forEach にはできない break( 繰り返しを途中で打ち切る ) や continue( その回だけ処理を飛ばして次に進む ) が使えるという特徴がある。

for (const fruit of fruits) {
  if (fruit === "みかん") {
    continue; // みかんのときだけ表示をスキップ
  }
  console.log(fruit);
}

reduce: 配列全体を 1 つの値にまとめる

forEach ・ map ・ filter に加えてもう 1 つ、配列を扱う上でよく登場するのが reduce である。配列の要素を先頭から順に 1 つの値へと集約していく。

const prices = [100, 200, 300];

const total = prices.reduce((sum, price) => sum + price, 0);
console.log(total); // 600

reduce は「それまでの集計結果 (sum) 」と「今見ている要素 (price) 」を受け取り、新しい集計結果を返す、という処理を配列の要素の数だけ繰り返す。最後の 0 は集計を開始する初期値である。
map や filter に比べると理解に少し時間がかかる関数だが、「合計を出す」「最大値を探す」「配列をオブジェクトに変換する」など応用範囲が広く、覚えておくと便利である。最初は無理に使いこなそうとせず、必要になったときに読み返す形で構わない。

for 文と forEach/map は、どちらを使うべきか

「昔ながらの for 文」と「 forEach や map のような配列専用メソッド」のどちらを使うべきかは、状況によって答えが変わる論点である。
forEach や map は書く量が少なく、意図 ( 加工したいのか、絞り込みたいのか ) がコードの見た目からも伝わりやすいという利点がある。一方で、処理を途中で打ち切りたい場合 (break で繰り返しを中断する場合 ) や、配列以外のもの ( 数値を使った単純な繰り返しなど ) を扱う場合には、昔ながらの for 文の方が素直に書けることもある。
どちらか一方が常に正しいという話ではなく、目的に応じて選ぶものだと捉えておくとよいだろう。

while 文 : 条件が満たされる間ずっと繰り返す

繰り返す回数があらかじめ決まっていない場合には、 while 文が使われる。

let count = 0;
while (count < 3) {
  console.log(`カウント: ${count}`);
  count++;
}

while は「条件が true である間、ずっと繰り返す」という文である。
繰り返しの中で条件が変化する処理 ( たとえば count++) を書き忘れると、条件が永遠に true のままになり、ブラウザが固まってしまう「無限ループ」に陥る。開発者ツールのコンソールで試していて反応がなくなった場合は、タブごと閉じて作業をやり直すのが確実である。

アドバイス ( 筆者の見解 )

この章の内容は、実際に手を動かして「表示される回数」や「表示される中身」を目で確認しながら覚えるのが一番の近道である。
特に map と filter は、頭の中だけで結果を予想しようとせず、 console.log() で毎回結果を出力しながら試すことを強くおすすめする。何度も繰り返すうちに、配列に対して「加工したいのか、絞り込みたいのか、ただ処理したいだけなのか」を先に考えるくせがついてくる。

関数とは、名前のついた処理のまとまり

これまでの章で書いてきたコードは、上から下に 1 回だけ実行されるものだった。しかし実際のプログラムでは「同じ処理を、違う値で何度も使い回したい」という場面がよく出てくる。
そこで使うのが関数である。関数は「入力 ( 引数 ) を受け取り、何らかの処理をして、出力 ( 戻り値 ) を返す」というひとまとまりの処理に名前をつけたものである。

function greet(name) {
  return `こんにちは、${name}さん`;
}

console.log(greet("田中")); // "こんにちは、田中さん"
console.log(greet("佐藤")); // "こんにちは、佐藤さん"

function というキーワードで関数を定義し、 ( ) の中に受け取る値 ( 引数、この例では name) を書く。 return の後ろに書いた値が、関数を呼び出した側に返ってくる。
一度定義してしまえば、 greet("田中") のように何度でも呼び出せる。

アロー関数という、もう 1 つの書き方

ES2015 以降の JavaScript では、関数を書くもう 1 つの方法として「アロー関数」という書き方も広く使われている 1 。

// 従来の書き方
function add(a, b) {
  return a + b;
}

// アロー関数
const add2 = (a, b) => {
  return a + b;
};

// 処理が1行で済むときは、さらに省略できる
const add3 = (a, b) => a + b;

前章の map や filter で (fruit) => fruit.toUpperCase() のように書いていたのが、まさにこのアロー関数である。短く書けることに加えて、配列メソッドに「その場で使い捨ての処理」を渡すような場面と相性がよいため、現在のコードでは非常によく見かける。

従来の function とアロー関数には、書き方の違い以外にも技術的な差 ( 関数の中で this という特別な値が指すものが異なる、など ) があるが、この差が問題になる場面はある程度 JavaScript に慣れてから遭遇するものである。この記事の段階では「同じようなことができる 2 つの書き方がある」という理解で十分で、まずはコードを読むときにどちらの形が出てきても戸惑わないことを目標にしよう。

引数のデフォルト値

関数を呼び出すときに値を渡さなかった場合の「デフォルト値」を、引数の宣言時に指定できる。

function greet(name = "ゲスト") {
  return `こんにちは、${name}さん`;
}

console.log(greet());       // "こんにちは、ゲストさん"
console.log(greet("田中")); // "こんにちは、田中さん"

スコープ : 変数が「見える」範囲

関数の中で let や const で作った変数は、その関数の外からは見えない。この「変数が有効な範囲」のことをスコープと呼ぶ。

function calculate() {
  const result = 42;
  console.log(result); // 42(関数の中からは見える)
}

calculate();
// console.log(result); // エラー:関数の外からresultは見えない

スコープがあることで、それぞれの関数の中で自由に変数名をつけても、他の関数の変数とうっかり混ざってしまう心配がなくなる。 let と const は { } で囲まれたブロックの範囲でスコープが区切られる「ブロックスコープ」という性質を持っており、これは if 文や for 文の { } にもあてはまる 2 。

関数を値として渡す : 高階関数という考え方

第 4 章で登場した map や filter は、 ( ) の中に関数そのものを渡していた。
JavaScript では関数を、数値や文字列と同じように「値の一種」として扱える。変数に入れることも、別の関数の引数として渡すこともできる。
このように「関数を受け取ったり返したりする関数」のことを高階関数と呼ぶ。

function repeatTwice(task) {
  task();
  task();
}

repeatTwice(() => console.log("こんにちは"));
// "こんにちは" が2回表示される

repeatTwice は、引数として受け取った task という関数を、自分の中で 2 回呼び出しているだけである。何を 2 回実行するかは、呼び出す側が自由に決められる。
この「処理そのものを引数として渡す」という考え方は、 map ・ filter ・ addEventListener( 第 7 章 ) ・ then( 第 8 章 ) など、この先の章でも繰り返し登場する、 JavaScript らしい書き方の 1 つである。

コラム ( 事実 ): 宣言する前に使うとどうなるか

let や const で宣言した変数は、実際に宣言される行に到達するまでの間、その変数名自体は認識されているのに値を読み書きしようとするとエラーになる、という特殊な期間がある。この期間は「一時的な死角」を意味する「 Temporal Dead Zone(TDZ) 」と呼ばれている 3 。
古い書き方の var では、宣言前に参照してもエラーにならず undefined が返ってくるため、両者は似ているようで挙動が異なる。実務でこの名称そのものを使う場面は多くないが、「宣言より前で let/const の変数を使おうとするとエラーになる」という現象自体はよく遭遇するので、覚えておくと役立つ。

アドバイス ( 筆者の見解 )

関数の名前のつけ方に少し時間をかけることをおすすめする。
function f(x) のような名前でも動作はするが、半年後の自分やチームメンバーが読んだときに「これは何をする関数か」が名前だけで伝わるようにしておくと、読み返すときの負担が大きく減る。 calculateTotalPrice や isValidEmail のように、「動詞 + 目的語」や「 is/has+ 状態」の形で名づけると意図が伝わりやすくなる、という慣習が広く使われている。

DOM とは何か

ブラウザは HTML ファイルを読み込むと、そのタグの入れ子構造をもとに「 DOM(Document Object Model) 」と呼ばれる、プログラムから操作できるオブジェクトの木構造を内部に作る。
JavaScript から見たとき、 HTML の見出しや段落、ボタンなどは、 DOM というオブジェクトとして触れる対象になる。「ページの見た目や中身を JavaScript から書き換える」というのは、実際には「この DOM というオブジェクトを操作する」ことにほかならない。

要素を探す :querySelector

DOM を操作する第一歩は、操作したい要素を見つけることである。もっとも汎用的な方法は document.querySelector() で、 CSS と同じセレクタの書き方で要素を探せる。

<h1 id="title">元のタイトル</h1>
<p class="intro">元の説明文</p>

<script>
  const titleEl = document.querySelector("#title");
  const introEl = document.querySelector(".intro");
</script>

CSS で #title や .intro のように書いてスタイルを当てた経験があれば、 querySelector() のカッコの中身は見覚えのある書き方のはずだ。同じセレクタの知識がそのまま JavaScript でも活きる。
複数の要素をまとめて取得したいときは、 document.querySelectorAll() を使うと、条件に合うすべての要素の一覧が得られる。

中身やスタイルを書き換える

要素が取得できたら、その中身や見た目を書き換えられる。

const titleEl = document.querySelector("#title");

titleEl.textContent = "新しいタイトル";       // 文字だけを書き換える
titleEl.style.color = "red";                  // 見た目(CSS)を直接書き換える

textContent は要素の中の文字だけを書き換える。
innerHTML という似たプロパティもあり、こちらは HTML タグを含んだ文字列をそのまま挿入できて便利だが、ユーザーが入力した文字列をそのまま innerHTML に代入すると、意図しないタグやスクリプトが実行されてしまう危険がある。表示するのが単なる文字列なら textContent を使い、 HTML タグを含む内容を挿入する必要がある場合だけ、その内容の出どころを十分に確認した上で innerHTML を使う、という使い分けが安全側の基本方針である。

クラスを操作して、見た目の切り替えを CSS に任せる

色や大きさを 1 つずつ style で直接指定する方法のほかに、あらかじめ CSS で用意しておいたクラスを JavaScript から付けたり外したりする方法もよく使われる。

<style>
  .highlight { background: yellow; font-weight: bold; }
</style>

<p id="message">お知らせ</p>

<script>
  const messageEl = document.querySelector("#message");
  messageEl.classList.add("highlight");    // クラスを追加
  // messageEl.classList.remove("highlight"); // クラスを外す
  // messageEl.classList.toggle("highlight"); // あれば外す、なければ付ける
</script>

この方法の利点は、「何色にするか、どんな見た目にするか」というデザインの詳細は CSS 側にまとめておき、 JavaScript 側は「このクラスを付けるか外すか」という状態の切り替えだけに専念できることである。デザインを変更したくなったとき、 JavaScript のコードを触らず CSS だけ直せばよいという役割分担ができるため、 style を直接書き換える方法よりも保守しやすいとされることが多い書き方である。
とはいえ、動的に計算した値 ( たとえばマウスの位置に応じた座標 ) を反映するような場面では style を直接操作する方が自然な場合もあり、状況に応じて両方を使い分けることになる。

新しい要素を作ってページに追加する

既にある要素を書き換えるだけでなく、新しい要素そのものを JavaScript で作り、ページに追加することもできる。

const list = document.querySelector("#fruit-list");

const newItem = document.createElement("li");
newItem.textContent = "パイナップル";
list.appendChild(newItem);

document.createElement() で新しい要素を作り、 textContent などで中身を設定し、既存の要素に対して appendChild() で追加する、という 3 ステップである。この組み合わせは、一覧に項目を追加する機能など、実際の Web ページで非常によく使われるパターンである。

要素を消す・順番を変える

追加だけでなく、既存の要素を取り除いたり、位置を調整したりする操作もよく使う。

const item = document.querySelector("#unwanted-item");
item.remove(); // その要素をページから取り除く

const list = document.querySelector("#fruit-list");
const firstItem = document.createElement("li");
firstItem.textContent = "先頭に追加する要素";
list.prepend(firstItem); // 一覧の先頭に追加(appendChildは末尾に追加)

addEventListener の基本形

前章まではページが読み込まれた瞬間に一度だけ実行されるコードを書いてきた。ここからは「ユーザーがボタンをクリックしたら」「フォームを送信したら」のように、ユーザーの操作をきっかけに動くコードを扱う。
これを実現するのが addEventListener() である。

<button id="my-button">クリックしてね</button>

<script>
  const button = document.querySelector("#my-button");

  button.addEventListener("click", () => {
    alert("クリックされました");
  });
</script>

addEventListener() には「どんな種類の操作に反応するか ( この例では "click") 」と「実際に反応したときに実行する処理 ( 関数 ) 」の 2 つを渡す。ボタンがクリックされるたびに、渡した関数がブラウザによって自動的に呼び出される仕組みである。

よく使うイベントの種類

イベント名発生するタイミング
click 要素がクリックされたとき
input 入力欄の値が変化するたびに
submit フォームが送信されたとき
keydown キーが押されたとき
DOMContentLoadedHTML の読み込みと解析が完了したとき

DOMContentLoaded はページ全体に対して使うイベントで、「ページの中身 (DOM) が揃うまで待ってから、 JavaScript の処理を開始したい」という場面で使われる。 <script> タグを <head> 内に置く場合など、 DOM がまだ準備できていないタイミングでコードが実行されてしまう可能性がある構成では、このイベントで処理の開始を待つ書き方がよく使われる。

入力値を受け取る

フォームの入力欄の値を取得するには、 value プロパティを使う。

<input type="text" id="name-input">
<button id="submit-button">送信</button>
<p id="result"></p>

<script>
  const input = document.querySelector("#name-input");
  const button = document.querySelector("#submit-button");
  const result = document.querySelector("#result");

  button.addEventListener("click", () => {
    const name = input.value;
    result.textContent = `こんにちは、${name}さん`;
  });
</script>

この例では、ボタンがクリックされた瞬間の input.value( 入力欄の中身 ) を読み取り、それをもとに別の要素の表示を書き換えている。「入力を受け取る」「加工する」「表示する」という 3 ステップは、フォームまわりの処理でくり返し登場する基本パターンである。

フォームの送信を止める :preventDefault

<form> タグは、通常は送信ボタンが押されるとページ全体が再読み込みされる。 JavaScript だけでその場の表示を切り替えたい場合、この標準の動きを止める必要がある。

const form = document.querySelector("#my-form");

form.addEventListener("submit", (event) => {
  event.preventDefault(); // ページの再読み込みを止める
  console.log("フォームが送信されました(ページは再読み込みされません)");
});

イベントに反応する関数の引数 ( この例での event) には、発生したイベントに関する情報がまとまって渡される。 event.preventDefault() は「このイベントが本来引き起こすはずだった標準の動作をキャンセルする」という命令で、フォームの submit イベント以外でも、リンクのクリックによるページ遷移を止めたい場合などに使われる。

イベント委譲 :1 つずつ登録するか、まとめて登録するか

一覧の項目それぞれにボタンがあり、どのボタンが押されても似た処理をしたい、という場面を考える。項目 1 つずつに addEventListener() を登録する方法のほかに、親要素 1 つだけにイベントを登録し、どの子要素が実際にクリックされたかを後から判定する「イベント委譲」という方法もよく使われる。

<ul id="fruit-list">
  <li>りんご</li>
  <li>みかん</li>
</ul>

<script>
  const list = document.querySelector("#fruit-list");

  list.addEventListener("click", (event) => {
    console.log(`クリックされたのは: ${event.target.textContent}`);
  });
</script>

event.target には、実際にクリックされた要素そのものが入る。 <ul> の中でどの <li> がクリックされても、そのクリックは親である <ul> まで伝わってくる ( これを「イベントのバブリング」と呼ぶ ) 性質を利用している。

この方法には、要素の数が多いときにイベント登録の処理が 1 回で済むという利点や、後から <li> を動的に追加した場合でも、新しい要素に対して改めて addEventListener() を書き直す必要がないという利点がある。
一方で、素直に「それぞれの要素に直接登録する」方法の方が、コードを読んだときに「何が何に反応しているか」を追いやすいという見方もある。要素の数が少なく、後から動的に増減しない場面では、無理にイベント委譲を使わなくても構わない。

コラム ( 事実 ):HTML 属性に直接書く onclick という古い方法

古い Web ページのソースでは、 <button onclick="doSomething()"> のように、 HTML タグの属性として直接 JavaScript の処理を書き込むスタイルもよく見かける。この書き方自体は今もブラウザで動くが、 HTML( 構造 ) と JavaScript( 振る舞い ) が同じ場所に混ざってしまい、規模が大きくなると管理が難しくなるため、現在は本章で紹介した addEventListener() を使い、 HTML と JavaScript のファイルを分離しておく書き方が広く好まれている。
ただし、ごく小規模な検証用コードやプロトタイプで onclick 属性を手早く使うこと自体が誤りというわけではなく、目的に応じた判断である。

今日の実習

テキスト入力欄・ボタン・空の <ul> を用意し、「入力欄に文字を入れてボタンを押すと、その文字が新しい <li> としてリストに追加され、入力欄は空になる」というミニアプリを作ってみよう。前章の DOM 操作 (createElement ・ appendChild) と、本章のイベント処理を組み合わせる練習になる。

「時間がかかる処理」をどう扱うか

これまでのコードはすべて、上から下へ順番に、しかも一瞬で実行される前提で書かれていた。しかし実際の Web ページでは「サーバーにデータを問い合わせて、返ってくるまで待つ」といった、時間のかかる処理がよく登場する。
このとき、返事が返ってくるまでブラウザ全体の動きを止めてしまう ( ボタンも押せない、画面もスクロールできない ) のは、多くの場合望ましくない。そこで JavaScript には「時間のかかる処理を裏側で進めておいて、終わったら結果を受け取る」という非同期処理の仕組みが用意されている。

もっとも単純な例が setTimeout() である。

console.log("1番目");

setTimeout(() => {
  console.log("3番目(2秒後)");
}, 2000);

console.log("2番目");

このコードを実行すると、「 1 番目」「 2 番目」がすぐに表示され、 2 秒経ってから「 3 番目」が表示される。 setTimeout() を呼び出した時点でコードの実行はいったん先に進み、指定した時間が経過した後で、渡しておいた関数が呼び出されるという流れである。
この「先に進んでおいて、後から結果を受け取る」という考え方が、非同期処理全体の土台になる。

Promise という「結果の予約券」

非同期処理の結果を扱いやすくするための仕組みが Promise である。 Promise は 2015 年の ES2015 で標準化された機能で 1 、「今はまだ結果がないが、いずれ成功か失敗の結果が届く」という状態を表すオブジェクトである。
よく「レストランの順番待ちの呼び出しベル」にたとえられる。ベルを受け取った時点では料理はまだできていないが、「いずれ鳴る」ことが約束されていて、鳴ったら結果 ( 料理 ) を受け取れる。

function waitAndGreet() {
  return new Promise((resolve) => {
    setTimeout(() => {
      resolve("お待たせしました");
    }, 1000);
  });
}

waitAndGreet().then((message) => {
  console.log(message); // 1秒後に "お待たせしました"
});

.then() に渡した関数は、 Promise の処理が成功したときに、その結果 ( この例では "お待たせしました") を受け取って呼び出される。

async/await:Promise をもっと読みやすく書く

.then() を使った書き方は、非同期処理が何段階も連なると読みにくくなりがちである。
そこで 2017 年の ES2017 で追加されたのが async/await という書き方である 2 。これを使うと、同じ処理を見た目上ほとんど「上から下に順番に書いたコード」のように書ける。

async function main() {
  console.log("処理を開始します");
  const message = await waitAndGreet(); // ここで結果が届くまで待つ
  console.log(message);
  console.log("処理を終了します");
}

main();

await は「 Promise の結果が届くまでここで待つ」という意味の書き方で、これを使う関数には async という印をつける必要がある。内部的には Promise の仕組みがそのまま使われているが、見た目が同期的なコードに近づくため、多くの開発者にとって .then() を連ねる書き方より読みやすいとされている。
ただし、これは「 .then() が常に劣っている」という意味ではなく、複数の非同期処理を並行して走らせたい場合などでは .then() や、それと組み合わせる Promise.all() のような書き方が適していることもある。

fetch() でサーバーからデータを取得する

非同期処理がもっとも活躍する場面の 1 つが、サーバーとの通信である。
ブラウザに標準で備わっている fetch() という関数を使うと、指定した URL にリクエストを送り、返ってきたデータを扱える。 fetch() は WHATWG という標準化団体が策定する仕様 (Fetch Standard) で定義されており、 2015 年前後から主要ブラウザに順次実装された 3 。

async function loadData() {
  const response = await fetch("https://example.com/api/data");
  const data = await response.json(); // JSON形式のデータを取り出す
  console.log(data);
}

loadData();

fetch() は最初にリクエストを送った時点でのレスポンス ( 通信の応答 ) を Promise として返し、続けて response.json() で、その中身を JavaScript のオブジェクトとして取り出している。ここで登場する「 JSON 」というデータ形式については、次章で改めて扱う。

非同期処理の中でエラーに備える

通信が失敗したり、サーバーがエラーを返したりする可能性は常にある。 async/await を使ったコードでエラーに備えるときは、次章で扱う try/catch をそのまま組み合わせられる。

async function loadData() {
  try {
    const response = await fetch("https://example.com/api/data");
    const data = await response.json();
    console.log(data);
  } catch (error) {
    console.log("読み込みに失敗しました:", error.message);
  }
}

try の中で await している処理のどこかが失敗すると、その時点で処理が catch の方へ移る。通信のように失敗する可能性がある非同期処理は、常にこの形でエラーに備えておくと安全である。

複数の非同期処理を同時に進める :Promise.all

await を複数回、上から順番に書くと、 1 つ目が終わってから 2 つ目が始まる、という具合に処理が直列に進む。互いに関係のない複数の非同期処理を同時に進めたい場合は、 Promise.all() を使うと、すべてが終わるのを一度に待てる。

async function loadAll() {
  const [users, posts] = await Promise.all([
    fetch("https://example.com/api/users").then((r) => r.json()),
    fetch("https://example.com/api/posts").then((r) => r.json())
  ]);
  console.log(users, posts);
}

2 つの fetch を順番に await すると、待ち時間が単純に足し算されてしまうが、 Promise.all() でまとめて渡すと、両方を同時に進めておいて、両方とも終わった時点で先に進める。すべての非同期処理を Promise.all() にすればよいわけではなく、「 2 つ目の処理が 1 つ目の結果を必要とする」場合には、そのまま順番に await する書き方が必要になる。

「なぜ結果がすぐ返ってこないのか」「 await を書き忘れるとどうなるか」といったことは、説明を読むだけでなく実際に console.log() を複数箇所に仕込んで、処理がどの順番で実行されているかを自分の目で追いかけると理解が進みやすくなる。一度ですべてを飲み込もうとせず、今日は「時間のかかる処理は、先に進んでおいて後から結果を受け取る」という大枠だけ持ち帰れば十分である。

エラーメッセージは敵ではない

ここまでの 8 日間で、意図しないエラーメッセージに何度も遭遇してきたはずだ。エラーメッセージは「何かがうまくいかなかった」という知らせであると同時に、「どこで」「なぜ」うまくいかなかったのかという手がかりでもある。
エラーを読み解く力は、コードを書く力と同じくらい実務で重要である。

よく出会う代表的なエラーの種類を紹介する。

エラーの種類典型的な原因
SyntaxError カッコや引用符の閉じ忘れなど、文法そのものの誤り
ReferenceError 定義していない変数・関数名を使おうとした
TypeErrornull や undefined に対してプロパティやメソッドを呼び出そうとした、など型に関する誤り

特に TypeError: Cannot read properties of null のようなメッセージは、第 6 章で触れた「 querySelector() が要素を見つけられず null を返し、その null に対して .textContent などを呼び出そうとした」場面で非常によく発生する。エラーメッセージに出てくる行番号は、多くの場合「原因そのものの行」ではなく「症状が表面化した行」を示しているだけのこともあるため、その行だけでなく、そこに至るまでの変数の中身を順に確認していく姿勢が大切である。

  • Console パネル :console.log() の出力先であると同時に、その場で JavaScript を直接実行できる場所でもある。エラーが起きたときは、赤字でエラーメッセージとスタック ( どの関数からどの関数が呼び出されて、どこでエラーになったかの経路 ) が表示される。
  • Sources パネル : 実際に読み込まれている .js ファイルの中身を表示し、特定の行に「ブレークポイント」を置いて、そこで処理を一時停止させながら変数の中身を 1 つずつ確認できる。
  • Network パネル : 前章の fetch() のような通信が、どの URL に対して、どんなデータをやり取りしているかを確認できる。

console.log() をコードのあちこちに埋め込んで値を確認する方法は手軽で今でも広く使われるが、 Sources パネルのブレークポイント機能を使うと、コードを一切書き換えずに処理を一時停止して調べられるため、複雑な処理を追いかけるときには特に有効である。どちらか一方だけを使うのではなく、簡単な確認は console.log() で、込み入った処理の追跡はブレークポイントで、というように使い分けると効率がよくなる。

try/catch でエラーを予測して備える

エラーが起きる可能性がある処理を、あらかじめ「エラーが起きても止まらないように」書いておくこともできる。

try {
  const data = JSON.parse("これは正しいJSONではない");
  console.log(data);
} catch (error) {
  console.log("データの読み込みに失敗しました:", error.message);
}

try の中に書いた処理でエラーが発生すると、そこで処理が中断され、 catch の中の処理に切り替わる。特に外部から届くデータを扱う場面 ( たとえば前章の fetch() で取得したデータの形式が想定と違った場合など ) では、 try/catch でエラーに備えておくことで、アプリ全体が予期せず止まってしまう事態を避けられる。

JSON:JavaScript からも他の言語からも読み書きしやすいデータ形式

前章の response.json() や、上のコード例に出てきた JSON.parse() で触れている JSON(JavaScript Object Notation) は、データをやり取りするための軽量なテキスト形式である。名前の通り JavaScript のオブジェクトの書き方をもとにしているが、現在では JavaScript 以外の多くのプログラミング言語でも読み書きできる、事実上の共通フォーマットとして使われている。
この形式は 2000 年代初頭に Douglas Crockford 氏によって整理され、 json.org というサイトで仕様として公開されたのが始まりとされ、 2006 年にはインターネット標準の 1 つ (RFC 4627) として正式に仕様化された 1 。

const jsonText = '{"name": "田中", "age": 34}';

const obj = JSON.parse(jsonText);   // JSON文字列 → JavaScriptのオブジェクト
console.log(obj.name);              // "田中"

const backToText = JSON.stringify(obj); // JavaScriptのオブジェクト → JSON文字列
console.log(backToText);

JSON.parse() と JSON.stringify() は対になる関数で、「テキストとオブジェクトを行き来させる」役割を持っている。サーバーとブラウザの間でデータをやり取りするとき、多くの場合この JSON 形式に変換してから送受信が行われる。

ファイルを分割する :ES Modules

第 1 章で「 HTML と JavaScript をファイルとして分ける」話をしたが、 JavaScript のコード自体も、規模が大きくなれば複数のファイルに分けたくなる。そのための標準の仕組みが ES Modules(import/export) である。

// math.js
export function add(a, b) {
  return a + b;
}

// main.js
import { add } from "./math.js";
console.log(add(2, 3)); // 5

使う側は <script> タグに type="module" を指定する。

<script type="module" src="main.js"></script>

この仕組みの文法自体は ES2015 で定義されたが、ブラウザが実際に <script type="module"> を解釈できるようになったのは少し遅れて、 2017 年前後のことである。当時の Web 開発者向けの技術記事によれば、 2017 年 3 月にリリースされた Safari 10.1 が先陣を切り、同年のうちに Chrome ・ Firefox ・ Edge も追随したと報告されている 1 。
現在の主要ブラウザでは ES Modules は標準的に使える機能になっている。

モジュールに分けることで、「 1 つのファイルに全部書く」状態から抜け出し、機能ごとにファイルを整理できる。この先、複数人でのチーム開発や、外部のライブラリを取り込む場面では、ほぼ前提として登場する考え方である。

フレームワークという選択肢

ここまでの 10 日間で学んだのは、いわば「素の JavaScript(Vanilla JS) 」と呼ばれる、追加の道具立てなしの基本文法である。
実際の大規模な Web サービス開発では、 React ・ Vue ・ Svelte といった「フレームワーク」または「ライブラリ」と呼ばれる仕組みを使うことが多くある。これらは、 DOM 操作 ( 第 6 章 ) やイベント処理 ( 第 7 章 ) を、より効率的に、大規模なアプリケーションでも破綻しにくい形で書けるようにするための道具である。

「フレームワークを使うべきか、素の JavaScript のままでよいか」は、プロジェクトの規模や目的によって答えが変わる論点で、どちらか一方が常に正解というものではない。
小規模なページの部分的な演出や、学習目的であれば、素の JavaScript のままで十分に目的を達成できる。一方で、画面の状態が複雑に絡み合う大規模なアプリケーションを複数人で開発する場合には、フレームワークが提供する「決まったパターンに沿って書く」という制約が、コードの見通しや保守性を保つ助けになる。
逆にフレームワークには、学習コストや、ビルドツールなど周辺環境の準備が必要になるという負担もある。本稿で身につけた変数・関数・ DOM ・イベント・非同期処理の知識は、どのフレームワークを選ぶ場合であっても土台として必要になるものなので、遠回りにはならない。

AI コーディング支援とのこれからの付き合い方

本稿を読み終える頃には、 AI のコーディング支援が書いてくれる JavaScript のコードを、以前よりずっと具体的に読めるようになっているはずだ。「これは配列を filter しているんだな」「ここで await を使っているのは、 fetch の結果を待っているからだな」というように、コードの意図を追える状態は、 AI との付き合い方そのものを変える。

AI に書いてもらったコードをそのまま使うか、内容を理解した上で使うかの違いは、動いている間は見えてこない。違いが表面化するのは、多くの場合「思ったのと違う動きをしたとき」「エラーが起きたとき」「後から機能を追加したくなったとき」である。
そうした場面で、コードの構造を自分でも読み解けることは、 AI への質問の精度を上げ、遠回りを減らすことにつながる。本稿で得た「読む力」は、 AI に頼らず全部自分で書けるようになることそのものよりも、 AI との共同作業をより効果的にすることに、より直接役立つはずである。

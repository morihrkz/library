費用から考えるウェブサイトの作り方

そのサイト、本当に「動的」である必要がありますか

動的である必要のないサイトなら、 GitHub Pages に静的サイトを構築することで、サーバー費用を無くせます。

ログインもコメントも決済もないサイトのためにレンタルサーバーを借りる必要はありません。

ウェブサイトを持とうとすると、たいていの人はまず「レンタルサーバーを借りて、 WordPress を入れる」という道を選びます。それが当たり前だと思われているからです。しかしその当たり前は、月々の請求書と、更新作業の手間という形で、毎年払い続ける費用になります。

この記事が問いかけたいのは、たった一つのことです。そのサイトは、その費用を払うだけの「動的な機能」を本当に使っていますか。使っていないのなら、サーバー費用は削れます。

よくある構成（レンタルサーバー＋ WordPress ）
年 7,000 〜 20,000 円
サーバー月額（ 500 〜 1,500 円程度）＋ドメイン維持費。加えて、更新・保守にかかる手間の時間。
この記事が勧める構成（ GitHub Pages ＋静的サイト）
年 1,000 〜 4,000 円
サーバー費用は 0 円。かかるのはドメイン維持費だけ。独自ドメインはそのまま使えます。
独自ドメインでサイトを運用する費用は、性質の違う二種類に分かれます。
ひとつはファイルを置いておくサーバー費用、もうひとつはドメイン名を持ち続けるためのドメイン維持費用です。
この記事でゼロにできると言っているのは前者だけです。ドメイン維持費用（年間 1,000 〜 4,000 円程度が目安）は、どの方法を選んでも毎年必ず発生します。
この記事の流れ
  1. 「動的が既定」という習慣が、どこで費用を生んでいるのか
  2. 静的サイトにすると、その費用のどこが消えるのか
  3. 自分のサイトが静的で足りるかどうかを、どう判断するか
  4. GitHub Pages で独自ドメインのサイトを公開する具体的な手順
  5. すでに WordPress で運用しているサイトを移すときの進め方

第１部「動的が既定」という習慣が、費用を生んでいる

1-1. なぜ WordPress が当たり前になったのか

2010 年代から 2020 年代の前半にかけて、 WordPress は CMS （コンテンツ管理システム）の中で圧倒的なシェアを占める、代表的な選択肢になりました。ドメインを取り、サーバーを借り、 WordPress を入れ、テーマを選び、プラグインをいくつか足せば、ウェブの仕組みを深く理解しなくても記事を公開できる。これは大きな功績でした。

ただし、普及していることとそのサイトに適していることは別の話です。 WordPress が広まった背景には、当時「手書きの HTML ファイルを何百枚も管理するのは現実的でない」という切実な問題があったことに加え、オープンソースであること、テーマ・プラグインのエコシステムが育ったこと、対応するレンタルサーバーが普及したことなど、複数の要因が重なっています。その前提が今も自分のサイトに当てはまるかどうかは、あらためて確かめる価値があります。

1-2. 動的サイトは「常時動いている一つのソフトウェア環境」

WordPress のような CMS （コンテンツ管理システム）で作られたサイトは、ページを見るたびにサーバー内のプログラム（ PHP など）が動き、データベースから記事の内容を取り出して、その場で HTML を組み立てて返します。これを動的サイトと呼びます。

一方の静的サイトは、あらかじめ完成させておいた HTML / CSS / 画像などのファイルを置いておくだけの仕組みです。アクセスが来たら、サーバーは「今から組み立てる」のではなく「もう完成しているファイルをそのまま渡す」だけです。

図１：　動的サイトと静的サイトの、リクエストごとの処理の違い

違いは「 HTML をいつ、どこで作るか」だけです。そしてこの違いが、そのまま費用の違いになります。
動的サイトは、誰もアクセスしていない夜中でも PHP とデータベースを動かせる状態で待機させておく必要があり、その待機場所の家賃が月額のレンタルサーバー費用です。
静的サイトには待機させるものがないので、ファイルを置く場所さえあれば済みます。

1-3. 請求書に載る費用と、載らない費用

費用はサーバー代だけではありません。動的サイトを持つということは、一式のソフトウェア環境を自分の責任で管理し続けるということです。 WordPress 本体、テーマ、複数のプラグイン、 PHP のバージョン、データベース、管理者アカウント。これらはいずれも更新が必要で、放置すると脆弱性の入り口になります。

費用の種類動的サイト（レンタルサーバー＋ WordPress ）静的サイト（ GitHub Pages ）
サーバー費用月 500 〜 1,500 円程度（年 6,000 〜 18,000 円）0 円
ドメイン維持費年 1,000 〜 4,000 円程度年 1,000 〜 4,000 円程度（同じ）
SSL 証明書無料の場合が多いが、有料オプションのことも0 円（標準で用意される）
更新・保守の手間本体・テーマ・プラグインの更新、脆弱性情報の確認、バックアップ、不具合対応ほぼ不要（更新すべきプログラムがない）
外注する場合の保守費月数千円〜数万円になることもある原則不要

実際、 2026 年 7 月にも WordPress は深刻度の高い脆弱性を修正するセキュリティリリースを行っています。
これは WordPress が特別に危ないという話ではありません。十分に複雑なソフトウェアには脆弱性が見つかるのが当たり前で、動的サイトを持つとはその更新作業を引き受けることだ、という当たり前の事実を示しているだけです。

月 30 ページほどの会社案内サイトで、更新は月に一、二回。会員登録も買い物かごもない。それでも管理者は、本体の更新、プラグインの互換性、脆弱性情報、バックアップ、 PHP のバージョン、管理者アカウントの棚卸しを見続けることになります。受け取っている価値に見合っているかを、一度だけ考えてみる価値があります。

第２部静的サイトにすると、費用のどこが消えるのか

2-1. 「静的」とは表現が貧しいという意味ではない

静的サイトと聞いて、古い時代の素朴なホームページを思い浮かべる必要はありません。静的サイトでも、画面幅に応じたレイアウト、アニメーション、動画、画像の最適化、地図、検索、フォーム、アクセス解析、外部サービスとの連携は普通に使えます。この記事のページ自体も静的な HTML ファイル一枚です。

静的か動的かは、見た目ではなくページの HTML を作る場所の話です。訪問者が来るたびにサーバーで作るのが動的、公開する前に作り終えておくのが静的。それだけの違いです。

2-2. なぜ GitHub Pages は無料で使えるのか

GitHub は、プログラムのソースコードを保存・共有するための世界最大級のサービスです。 GitHub Pages は、その中にある「リポジトリ（ファイルの保管庫）」の中身を、そのままインターネット上のウェブサイトとして公開できる機能です。

静的サイトの配信は「置いてあるファイルをそのまま返すだけ」なので、サーバー側の負荷が小さく、提供する側のコストも低く済みます。これが無料で提供できる理由のひとつです（利用者に GitHub のエコシステムを使ってもらう狙いもあります）。この記事が想定するような会社案内・ポートフォリオといった一般的な使い方であれば、容量やアクセス数の制限内で費用は基本的にかかりません。

注意：　商取引を主目的とするサイトには制限があります
GitHub 公式は、オンラインビジネスや EC サイトなど、商取引を行うこと自体を主目的とするサイトを、無料の Web ホスティングとして運用することを認めていません。会社案内や事業紹介のように情報を掲載するだけのサイトはこの制限の対象外ですが、決済機能を持つ本格的な EC サイトを丸ごと無料で運用しようとする場合は、この制限に該当する可能性があります。
該当しそうな場合は GitHub 公式の利用条件を確認してください。

2-3. ５年間の総額を並べてみる

仮に、レンタルサーバーを月 1,000 円、ドメインを年 2,000 円として５年間の総額を比べるとこうなります。

図２：　５年間の費用試算（サーバー月 1,000 円、ドメイン年 2,000 円と仮定）

差額はおよそ 60,000 円です。金額そのものは構成によって上下しますが、重要なのは「使っていない機能のために、毎月お金を払い続けているかどうか」という点です。動的な機能を実際に使っているなら、この 60,000 円は正当な対価です。使っていないのなら、単に不要な出費です。

第３部あなたのサイトは、どちらで足りるか

3-1. 判断は、この一つの問いに集約される

訪問者がページを開くたびに、サーバー側で何かを計算したり保存したりする必要があるか。

必要が無いなら静的サイトで足ります。必要があるならその部分については動的な仕組みが要ります。それだけです。
「見栄えを良くしたい」、「スマートフォンに対応したい」、「画像をたくさん載せたい」などは、いずれも動的である理由になりません。

3-2. チェックリスト

次のうち、当てはまるものが無いなら、静的サイトで十分です。
  • □ 訪問者がアカウントを作り、ログインする
  • □ 訪問者がコメントや投稿を書き込み、それがサイトに保存される
  • □ 商品を売り、その場で決済する（在庫や注文を管理する）
  • □ 訪問者ごとに違う内容を出し分ける（会員ランク別の価格など）
  • □ 在庫数・予約枠・価格など、頻繁に変わるデータをその場で表示する
  • □ 複数の担当者が、承認フローを通しながら日常的に記事を書く

逆に、次のようなサイトは、ほぼ確実に静的サイトで足ります。

  • 自分の作品をまとめるポートフォリオサイト
  • 会社案内・事業紹介などのコーポレートサイト
  • 部活動やサークル、団体の紹介ページ
  • イベントやキャンペーンの告知ページ
  • プロフィールページ、名刺代わりのサイト
  • 製品マニュアルやドキュメントのページ
  • 更新頻度が低い、小規模なお店の紹介サイト

3-3. 要件別の早見表

やりたいこと静的サイト（ GitHub Pages ）備考
会社案内・事業紹介十分動的にする理由がほとんどない
お知らせ・ブログの掲載十分更新のたびにファイルを差し替える
ポートフォリオ・作品集十分画像中心でも問題なし
ドキュメント・マニュアル十分むしろ静的が向く
お問い合わせフォーム外部サービスで可フォーム専用の無料サービスを埋め込む
サイト内検索外部サービスで可外部の検索サービス、または小規模なら JavaScript で
コメント欄外部サービスで可コメント専用サービスを埋め込む
会員登録・ログイン動的が必要外部の認証サービスか、動的な仕組みを併用
商品販売・決済動的が必要専用の EC サービスを使うのが現実的（自前の EC を GitHub Pages だけで無料運用することは想定されていません）
予約・在庫のリアルタイム表示動的が必要その部分だけ外部サービスに任せる

3-4. 動的な部分は、外部サービスで足せる

ここが実務上いちばん大事な点です。サイトに一つ動的な要素があるからといって、サイト全体を動的にする必要はありません。お問い合わせフォームが欲しいという理由だけで WordPress とレンタルサーバーを維持しているケースは、非常によくあります。
フォーム、コメント、検索、アクセス解析、予約受付といった機能は、それぞれ専用の外部サービスを静的なページに埋め込むことで実現できます。サイト本体は静的なまま、必要な部分だけを外に持たせる。この形なら、サーバーを借りずに済みます。

3-5. 動的が必要なら、ためらわず動的にする

誤解のないように書いておくと、この記事は「 WordPress の利用をやめましょう」という話ではありません。会員機能や決済、複数人での編集ワークフローが本当に必要なサイトにとって、 WordPress は今も非常に優れた選択肢です。間違いは、「使う必要が無いのに使うこと」です。

考え方の順番を、こう入れ替えるだけです。
×　「サイトを作りたい」→「 CMS が要る」→「 WordPress を使おう」
○　「サイトを作りたい」→「実際にどんな機能が要るのか」→「それを最も単純に実現できる仕組みはどれか」

第４部実践： GitHub Pages で独自ドメインのサイトを公開する

ここからは実践編です。例として、高校生の「なつき」さんが、自分のイラスト作品をまとめたポートフォリオサイトを、独自ドメイン natsuki-works.com （架空の例です）で公開するケースで手順を追います。サーバーは一切借りません。

4-1. その前に：サイトが表示される仕組み

設定作業の意味を理解しておくために、ページが表示されるまでの流れを押さえておきます。インターネット上のサーバーは 203.0.113.25 のような「ＩＰアドレス」で区別されています。
人間が毎回この数字を覚えるのは大変なので、 example.com のような「ドメイン名」を使います。この二つを結びつける、インターネット全体の電話帳にあたる仕組みが DNS (Domain Name System) です。

図３： URL を入力してからページが表示されるまでの流れ

ここで押さえておきたいのは、「ドメイン」と「サーバー（ホスティング先）」はまったく別の契約だということです。ドメインは住所の名前を借りる権利、サーバーはファイルを置く場所。この二つを DNS がつなぎます。この記事でゼロにできるのは後者だけで、ドメインの費用は残るのは、そういう理由です。

役割何をするか費用
ドメインサイトの「住所の名前」を持つ権利を、期間を決めて借りる年 1,000 〜 4,000 円程度
サーバー（ホスティング）ファイルを置いて、リクエストが来たら返すGitHub Pages なら 0 円

4-2. 準備するもの

  • パソコン（ Windows でも Mac でも可）
  • メールアドレス（ GitHub アカウント作成用）
  • ドメイン取得費用を支払える手段（未成年のかたは保護者の同意・協力を得てください）
注意：　ドメインの取得や支払いは契約行為です。未成年のかたは、必ず保護者に相談し、了承を得たうえで進めてください。
この章で行う作業
  1. GitHub アカウントを作り、サイト用のリポジトリを用意する
  2. HTML ファイルを配置し、まずは GitHub 標準の URL で表示を確認する
  3. GitHub Pages を有効化する
  4. 独自ドメインを取得する
  5. DNS の設定で、独自ドメインと GitHub Pages を結びつける
  6. 常時 HTTPS 化を有効にする
1GitHub アカウントとリポジトリを作る

github.com にアクセスし、無料アカウントを作成します。ログインしたら、新しいリポジトリ（ファイルの保管場所）を作ります。名前は何でも構いませんが、ここでは natsuki-portfolio とします。

リポジトリは「 Public （公開）」に設定してください。 GitHub Pages で無料公開するには、多くの場合このリポジトリが公開状態である必要があります。

2 サイトのファイルを用意して配置する

まずは表示させることを優先し、次のような最小構成から始めます。凝ったデザインは後からいくらでも足せます。

natsuki-portfolio/
├── index.html
├── style.css
└── images/
    └── work1.jpg

index.html の最小限の中身は、たとえばこの様になります。

<!DOCTYPE html>
<html lang="ja">
<head>
  <meta charset="UTF-8">
  <title>なつきの作品集</title>
  <link rel="stylesheet" href="style.css">
</head>
<body>
  <h1>なつきの作品集</h1>
  <p>高校２年生、イラストが好きです。</p>
</body>
</html>

作成したファイルは、 GitHub のウェブ画面にある「 Add file 」→「 Upload files 」からドラッグ & ドロップするだけでも配置できます。コマンドに慣れているかたは git push でも構いません。

3GitHub Pages を有効化する

リポジトリの「 Settings 」タブ →「 Pages 」を開きます。「 Source 」で、公開したいブランチ（通常は main ）とフォルダ（通常はルート / (root) ）を選んで保存します。

数分待つと、 https://[username].github.io/natsuki-portfolio/ のような URL でサイトが公開されます。ここまでは完全に無料で、ドメインもまだ取得していません。まずはこの標準 URL できちんと表示されるかを確認してください。

ポイント：独自ドメインの設定は、あくまで「見た目の住所を差し替える」作業です。標準 URL でサイトが正しく動くことを確認してから次に進むと、うまくいかないときに原因を切り分けやすくなります。
4 独自ドメインを取得する

ドメインを販売している事業者（レジストラ）で、希望のドメイン名（例： natsuki-works.com ）が空いているか検索し、取得します。「お名前 .com 」、「 Cloudflare Registrar 」、「 Value Domain 」などが代表的です。

ドメインの種類（ .com / .net / .jp など）によって費用は異なり、年間 1,000 〜 4,000 円程度が目安です。取得後は基本的に一年ごとの更新制になります。更新を忘れると失効し、最悪の場合は他人に取得されてしまうため、自動更新の設定を必ず確認してください。

5DNS を設定して、ドメインと GitHub Pages をつなぐ

図 3 で説明した「電話帳」を書き換える作業です。取得したドメインの管理画面（ DNS 設定画面）で、次の 2 種類を設定します。

設定するレコード役割
A レコード（四つ）ドメインそのもの（例： natsuki-works.com ）を、 GitHub Pages のＩＰアドレスに向ける
CNAME レコードwww.natsuki-works.com のような別名を、 [username].github.io に向ける

A レコードに設定するＩＰアドレスは、 GitHub の公式ドキュメントに記載されている固定値を使います（ 185.199.108.153 のような 4 つのアドレスが案内されています）。値が変更されることもあるため、実際の設定時は必ず GitHub 公式の最新情報を確認してください。

あわせて、 GitHub 側のリポジトリ設定（ Settings → Pages → Custom domain ）に、使いたいドメイン名を入力して保存します。「 GitHub 側の設定」と「 DNS 側の設定」は、両方が揃って初めて機能します。片方だけでは正しく表示されません。

反映には時間がかかることがあります
DNS の設定変更は、インターネット全体にすぐ行き渡るわけではありません。 GitHub 公式も、 DNS の変更が反映されるまで最大 24 時間程度かかる場合があるとしています。数分で反映されることもあれば、半日ほど待つ必要があることもあります。設定直後にうまく表示されなくても、あわてずに時間をおいて再確認しましょう。
6 常時 HTTPS 化を有効にする

独自ドメインでの表示が確認できたら、 GitHub の Pages 設定画面で「 Enforce HTTPS 」を有効にします。これにより http:// でのアクセスも自動的に https:// に転送され、ブラウザの警告表示も避けられます。証明書の費用はかかりません。
（この項目は、 DNS の設定が反映されるまで有効化できないことがあります。）

4-3. つまずきやすいポイント

  • DNS の反映待ちを、設定ミスと勘違いする：　
    まずは時間を置いて再確認する
  • A レコードと CNAME を混同する：　
    ドメイン本体には A レコード、 www 付きには CNAME 、と役割が違う
  • GitHub 側の Custom domain 設定を忘れる：　
    DNS だけ設定しても、 GitHub 側にドメイン名を伝えていないと機能しない
  • ドメインの自動更新を切ってしまい、失効させる：　
    年に一度の更新は、カレンダーにリマインダーを入れておくと安心

第５部いま WordPress で運用しているサイトを移す場合

5-1. いちばんの失敗は「一度に全部作り直す」こと

すでに運用中のサイトがある場合、全面的な作り直しは腰が重い作業です。そこで、まずページを棚卸しし、性質ごとに三つに仕分けます。

  • ただの文書：　
    会社概要、事業内容、アクセス、沿革　→　そのまま静的化できる
  • 形が決まった繰り返しの文書：　
    お知らせ、製品紹介、実績　→　静的化できる（テンプレート化する）
  • 本当に動的な機能：　
    ログイン、決済、在庫表示　→　外部サービスに任せるか、その部分だけ残す

多くのサイトでは、上の二つが全体の大部分を占めます。まずそこだけを静的サイトに移し、残りを個別に検討すれば十分です。

5-2. URL は、むやみに変えない

移行のいちばん大事なルール：既存の URL を安易に変更しない。

既存の URL は、検索エンジン、他サイトからのリンク、 SNS の投稿、印刷物、メール、社内文書から参照されています。どうしても変える必要がある場合は、旧 URL から新 URL への転送（リダイレクト）を設定してください。

5-3. 「更新する人」が運用できるかを先に確かめる

技術的に優れた構成でも、実際に更新する担当者が扱えなければ運用は止まります。移行の前に、担当者が新しい手順でページを 1 枚更新できるかを試してください。ここで無理があるなら、ヘッドレス CMS （編集画面だけを外部サービスに任せ、公開されるサイトは静的なままにする仕組み）を検討する価値があります。

5-4. 解約は最後に

新しい静的サイトが独自ドメインで正しく表示され、主要なページの表示・リンク・フォームを一通り確認するまで、既存のレンタルサーバーは解約しないでください。
並行して動かし、問題がないと確認できてから解約するのが安全です。費用の削減が実現するのはこの最後の一手ですので、忘れずに解約手続きまで行ってください。

静的にしてもゼロにならないもの：ドメインの管理アカウント、 GitHub のアカウント、それらのパスワードの管理は引き続き必要です。静的サイトはページを配信する部分の攻撃対象を大幅に減らしますが、「公開する権限を持つアカウントを守る」という仕事は残ります。ただしこれは、プラグインを毎月更新し続けるより、ずっと単純な仕事です。

まとめ

  • ウェブサイトの費用は「サーバー費用」と「ドメイン維持費用」に分かれる。削れるのはサーバー費用のほうで、ドメイン維持費用はどの方法でも必ずかかる
  • 動的サイトは、アクセスのたびにサーバー側でページを組み立てるため、 PHP やデータベースを常時動かす場所（＝有料のレンタルサーバー）が要る
  • 静的サイトは完成済みのファイルを返すだけなので、 GitHub Pages のような無料ホスティングで足りる。しかも表示は高速化しやすく、更新すべきプログラムがないため保守の手間も小さい
  • 判断基準は一つ。訪問者が来るたびにサーバー側で計算・保存が必要か。不要ならサーバー代は払わなくてよい
  • フォームや検索など一部の動的な機能は、外部サービスを埋め込めば静的サイトのままで足せる。一部が動的だからといって、全体を動的にしない
  • 本当に会員機能や決済が必要なサイトでは、 WordPress は今も正しい選択肢。問題は、必要がないのに使い続けている場合だけ
  • GitHub Pages は個人利用や情報提供サイトを想定した無料サービスで、商取引を主目的とするサイトの丸ごとの無料ホスティングは想定されていない

必要なところは動的に、それで足りるところは静的に。この使い分けができれば、払わなくてよい費用は払わずに済みます。まずは自分のサイトを開いて、第３部のチェックリストに一つでも当てはまるかどうかを確かめるところから始めてみてください。

本記事は、実際のウェブサイト移行作業の経験と、静的サイト構成に関する技術記事をもとに、一般化して解説したものです。金額はいずれも 2026 年 8 月時点の一般的な目安であり、実際の費用は利用するサービスや契約内容によって異なります。ドメイン取得や DNS 設定の具体的な項目名・画面表示もサービスによって異なるため、作業前には各サービスの公式ドキュメントもあわせて確認してください。

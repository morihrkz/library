実録・作業記録

ウェブサーバーを GitHub Pages へ移行した記録

二年間にわたり更新していなかった自社ウェブサイトを、 WordPress が動くレンタルサーバーから GitHub Pages へ移しました。その顛末を記します。

旧環境 : WordPress / XServer 新環境 : GitHub Pages DNS : Xserver Domain 独自ドメイン : pyx.co.jp サーバー契約期限 : 2026 年 8 月 31 日

「もとのサーバーから HTML ファイルを GitHub Pages に移し、ドメインの向き先を変える。」
こう言うと、単純な作業に聞こえます。ところが実際に手を動かすと話は変わりました。
DNS はどの契約に属しているのか。設定は本当に引き継がれるのか。何を確認してから削除すべきなのか。
ひとつ判断を間違えれば、サイトだけでなくドメインへの到達性まで失います。そこで今回は、作業そのものだけでなく、次へ進んでよいと判断した根拠まで記録することにしました。

旧ネームサーバー
ns1.xserver.jp 〜 ns5.xserver.jp
サーバー契約に紐づく DNS
新ネームサーバー
ns1.xdomain.ne.jp 〜 ns3.xdomain.ne.jp
Xserver Domain 側の DNS

以下は、移行前に作った実行計画書と、実際の作業記録を突き合わせながらまとめ直したものです。計画どおりだった部分だけでなく、計画から外れた出来事、途中で判断を変えた理由、そして最後まで残った確認事項まで含めて記します。

注 : 旧サーバーの各種識別情報は、記事の趣旨に必要ないため伏せてあります。

1-1. 二年間、放置されていたサイト

pyx.co.jp は筆者の会社のサイトで、 WordPress を動かし、その環境で作ったものでした。
ところが二年間、記事の更新も、プラグインの更新なども、手を付けていない状態が続いていました。動いてはいるが、誰も世話をしていないサイトです。
そこに、レンタルサーバーの契約期限という具体的な締切がやってきました。残り三週間しかありません。契約は自動更新が設定されておらず、支払いを行わなければ、期限日にアカウントが自然に凍結される見込みでした。
この期限をきっかけに、「同じ構成のまま契約を更新するか」を考えることになりました。

1-2. 動的サイトと静的サイト

WordPress の様な CMS （コンテンツ管理システム）で作られたサイトは、アクセスが来るたびにサーバー内のプログラム（ PHP など）が動き、データベースから記事の内容を取り出して、その場で HTML を組み立てて返します。これを動的サイトと呼びます。
一方の静的サイトは、あらかじめ完成させておいた HTML / CSS / 画像などのファイルを置いておくだけの仕組みです。アクセスが来ても、サーバーは「今から組み立てる」のではなく「もう完成しているファイルをそのまま渡す」だけです。

図 1 : 動的サイトと静的サイトの、リクエストごとの処理の違い

「このサイトは、必ずしも WordPress の上に構築されている必要は無いのではないか。」
これが、作り直しを検討した最初の動機でした。
（なお、動的サイトを実現する手段は WordPress 以外にもありますが、便宜上、「動的サイト = WordPress 」としています。）

観点WordPress （動的サイト）静的サイト
サーバー側の構成データベース・ PHP ・常時稼働のプロセスHTML/CSS/JS のファイルのみ
セキュリティ面の脅威プラグイン・ログイン画面・データベースへの問い合わせなどが攻撃対象となり得る実質的にほぼ無い（配信するだけ）
保守の手間継続的な更新・パッチ適用・バックアップ・監視サーバー側の保守は、ほぼ不要
コンテンツ更新方法管理画面上での編集個別ファイルの編集と Git 操作

WordPress は世界中の膨大な数のサイトを支える優れたソフトウェアです。編集者が複数いて、日常的に記事を書き、コメント機能や複雑なワークフローを必要とするサイトにとっては依然として強力な選択肢です。
しかし pyx.co.jp はそれに該当するサイトではありませんでした。

1-3. 旧記事は移さず、新たなコンテンツを作った

もう一つ、早い段階で決めたことがあります。旧サイトの内容は一つも移行しないという判断です。
二年近く更新が止まっていた内容を、手間をかけて移し替える価値があるかを考えた結果でした。新サイトで当初公開する内容は仮の一枚のページのみとし、本格的な内容は落ち着いてから作り込むという方針にしました。

移行というと、今あるものをそのまま新しい場所に持っていく、と考えがちですが、価値が薄れた内容まで運び込む必要はありません。移すものが少なければ移行作業は軽くなります。

ここで一度、作業の手を止めました。期限が決まっている以上、行き当たりばったりで進めるのは危険です。作成日から数えて実質二週間ほどしかない期限でした。
AI に相談しながら、現状の整理・技術選定・作業順序・想定される落とし穴を、一つの文書にまとめていきました。以下は、その計画段階で分かったことの記録です。

2-1. ドメインとサーバーは別契約、という基本

まず前提として、「ドメイン」と「サーバー（ホスティング先）」は、別の契約です。
インターネット上のサーバーは 203.0.113.25 の様な「 IP アドレス」で区別されていますが、人間が毎回この数字を覚えるのは大変なので、 pyx.co.jp の様な「ドメイン名」を使います。
この二つを結びつける、インターネット全体の電話帳にあたる仕組みが DNS (Domain Name System) です。

図 2 : URL を入力してからページが表示されるまでの流れ

pyx.co.jp の場合、ドメインの登録先とレンタルサーバーの契約先はどちらも同じ事業者 (XServer) でした。同じ会社でも「ドメイン契約」と「レンタルサーバー契約」という別々の契約として管理されています。
ドメイン契約は前月のうちにすでに 2027 年まで支払い済みで確保されており、サーバー契約とは無関係に存続する状態でした。

2-2. 最大の論点：　サーバー契約をやめても DNS は生き残るか

計画段階でいちばん時間を使ったのが、この一点でした。レンタルサーバーの契約をやめたとき、ドメインの DNS 設定を編集する手段と、ドメイン名から IP アドレスを引く「名前解決」の仕組みは、どうなるのか。

これは類推だけでは確定できない問題でした。 XServer の公式案内には、期限を超過したサーバーアカウントについて「凍結が行われるとホームページへのアクセスやメールの送受信が行えなくなります」とだけ書かれており、「 DNS レコードの管理ができなくなる」とは明記されていませんでした。
一方で、 XServer には管理画面が二種類あり、役割が分かれていることも分かりました。

管理画面役割
XSever レンタルサーバー契約管理ページ
https://secure.xserver.ne.jp/xapanel/xserver/index		サーバーの各種設定（メールアカウント発行など含め）
XSever Domain 契約管理ページ
https://secure.xserver.ne.jp/xapanel/xdomain/index		ネームサーバーの管理、 DNS レコードの管理、 Whois 情報の管理

DNS レコードの管理は「 XSever レンタルサーバー契約管理ページ」ではなく、ドメイン契約に紐づく「 XSever Domain 管理ページ」の機能でした。
さらに、 XServer にはドメインだけを単独契約する利用者も存在し、そうした利用者も同じネームサーバー群を使っていることが公式マニュアルから読み取れました。
サーバー契約を一度も持たない利用者がこの仕組みを使えている以上、サーバー契約の有無が DNS 配信の前提条件になっているとは考えにくいと判断できました。

ただし、これは状況証拠の積み重ねにすぎません。実際に dig コマンドで pyx.co.jp の現在のネームサーバーを調べたところ、次のように、サーバー契約者専用のネームサーバーが設定されていることが分かりました。

$ dig +short NS pyx.co.jp
ns1.xserver.jp.  ns2.xserver.jp.  ns3.xserver.jp.
ns4.xserver.jp.  ns5.xserver.jp.

この 5 台は、レンタルサーバー契約者専用のネームサーバーです。このままではサーバー契約が凍結されると同時に、 DNS の管理も名前解決も同時に失う可能性があると分かりました。
憶測で進めるにはリスクが大きすぎたため、最終的には XServer のサポートへ直接問い合わせ、書面で回答を得ました。回答の要点は次の二点でした。

サポート回答の要点（ 8 月 16 日）
1. ドメインのみ契約している状態でも、ネームサーバーを Xserver Domain （サーバー契約に紐づかない、ドメイン契約側の DNS 管理機能）に設定すれば、引き続き DNS レコードの編集・管理が可能。
2. ns1.xserver.jp 〜 ns5.xserver.jp による名前解決は、レンタルサーバー契約者専用であり、サーバー契約が凍結されると使えなくなる。したがって、凍結前にネームサーバーを Xserver Domain へ切り替えておく必要がある。

この回答により、作業の前提が一点変わりました。サーバー契約が凍結される前に、ネームサーバーを Xserver Domain へ切り替える作業が、独立した必須工程として加わったのです（詳しくは第３部）。

図 3 : DNS にまつわる二つの機能が、どちらの契約に紐づいているか

2-3. ホスティング先の選定： GitHub Pages を採用

静的サイトの置き場所として GitHub Pages と Cloudflare Pages を比較しました。決め手は費用ではなく、変更点を少なく済ませられるかどうかでした。

比較項目GitHub PagesCloudflare Pages
Apex ドメイン（ pyx.co.jp 自体）への設定A レコード 4 件を追加するだけ。 DNS の管理主体を変更する必要がない真価を発揮するには、通常ドメインのネームサーバーを Cloudflare 自体に切り替える構成が推奨される
費用無料無料プランでもほぼ賄えるが、カスタムドメイン数などに制限がある
HTTPSリポジトリ設定で Enforce HTTPS を有効化。反映まで最大 24 時間程度自動発行・自動更新

すでに 2-2 で、ネームサーバーを Xserver Domain へ切り替えるという変更を一つ抱えていました。ここにさらに、ネームサーバーを Cloudflare へ切り替えるという、もう一段構成の異なる変更を重ねる必然性はないと判断しました。
8 月 31 日という動かせない期限の下では、変更点を最小化するほうが安全という考え方です。
GitHub Pages なら、 Xserver Domain 側の DNS レコード設定画面で A レコードを追加するだけで完結します。

あわせて、いわゆる静的サイトジェネレーターなども特に導入しないことにしました。公開する内容が準備中を示す一枚もののページである以上、ビルド工程を挟む理由がなかったためです。依存パッケージのない、単一の index.html として作成する方針にしました。
リポジトリは新規に pyx-site という名前で作成し、公開範囲は Public （公開）としました。無料プランでは、 Private （非公開）のリポジトリで GitHub Pages を有効化できないと、この段階で判明したためです。

2-4. 全体の実施順序

サーバー契約の期限日から逆算し、作業を六つの工程に分けました。上から順に実行すれば、前提を満たさないまま先に進んでしまうことがない並びです。

工程内容
工程 1移行前の保全： DNS レコードのバックアップ
工程 2ネームサーバーを Xserver Domain へ切り替える
工程 3サイト構築と、切替前の完成確認
工程 4旧 WordPress 環境の削除
工程 5DNS 切替（ GitHub Pages への向け先変更）
工程 6切替後の検証

工程 1 と工程 2 は、 DNS に一切手を触れる前後の関係にあるため、必ずこの順で行う必要があります。一方、工程 2 （ネームサーバー切替）と工程 3 （サイト構築）は互いに独立しているため、並行して進めることができました。

2-5. 順序を入れ替えてはいけない四箇所

作業の多くは前後させても支障ありませんが、次の四つは技術上・安全上の理由から順序が固定されます。計画段階でここを洗い出しておいたことが、後の工程で実際に役立ちました。

この順序なぜ入れ替えてはいけないか
現在の DNS 設定を控える
→ ネームサーバーを切り替える		切り替えでレコードが引き継がれなかった場合、控えが無ければ何も復元できない
標準 URL で動作を確認する
→ Custom domain を設定する		Custom domain を設定すると、標準 URL は独自ドメインへ転送されるようになり、確認手段として使えなくなる
GitHub 側で Custom domain を設定する
→ DNS レコードを設定する		先に DNS だけを向けると、そのドメインで第三者にサイトをホストされる状態が生じうる（ GitHub 公式が明記している）
新しいサイトの完成を確認する
→ 旧環境を削除する		削除後は元に戻せない

そして、実際の切り替えに入りました。ここから先は、計画書の中では数行だった作業が、ひとつずつ現実の判断になります。
計画どおりに進んだところもあれば、実際に設定を切り替えた瞬間に、計画とは違う答えが返ってきたところもありました。

3-1. 工程 1 ：移行前の保全、 DNS レコードのバックアップ

DNS に最初の変更を加える前に、現在の設定値を全件控えました。旧 WordPress のコンテンツ自体は移行しないため保全対象外ですが、 DNS 設定は失うと取り返しがつかないため、最優先で控える工程です。

dig +short NS pyx.co.jp
dig +short A pyx.co.jp
dig +short A www.pyx.co.jp
dig +short MX pyx.co.jp
dig +short TXT pyx.co.jp
タイプホスト名値
NSpyx.co.jpns1.xserver.jp 〜 ns5.xserver.jp
Apyx.co.jp（旧サーバーの IP アドレス）
Awww.pyx.co.jp（ apex と同一）
MXpyx.co.jp0 pyx.co.jp
TXTpyx.co.jpSPF レコード（メール送信元の指定）

この控えは、単なる念のためのメモではありませんでした。後で DNS レコードが引き継がれなかったときに、何が失われたのかを特定するための照合資料になりました。

MX と TXT(SPF) の 2 件は、「全レコードを漏れなく控える」という保全要件を満たすために機械的に記録したものです。 pyx.co.jp のメールアドレスは使用したことがなく、今後も使う予定がなかったため、メール関連の移行・保全そのものは検討対象から外しました。

あわせて、 XServer アカウント（ドメイン契約管理ページ）にログインし、 DNS レコード設定画面をスクリーンショットで保存しました。 dig の結果は管理画面上の表示と完全には一致しない場合があるため、両方を控えておくのが安全です。控えは Git リポジトリとは別の、ローカルの控え用フォルダに保存しました。
この控えは、後の工程で実際に役に立ちました。ただし戻すためではなく、戻さなくてよいと判断するために使いました。詳しくは次項に記します。

3-2. 工程 2 ：ネームサーバーを Xserver Domain へ切り替える

XServer アカウントの管理画面で「ネームサーバーの設定」を開き、ネームサーバーを Xserver Domain （サーバー契約に依存しない、ドメイン契約側の標準 DNS 管理機能）に切り替えました。切り替え自体は、管理画面上の一操作で完了します。

切り替えの反映確認は、必ず権威サーバーへ直接おこないました。

# 委任情報（レジストリ側）
dig @a.dns.jp pyx.co.jp NS +norecurse
# 切替後の権威サーバーが実際に何を持っているか
dig @ns1.xdomain.ne.jp pyx.co.jp A

ここで、計画書にはなかった事実が一つ現れました。切り替えは成功しましたが、それまで設定されていた DNS レコードは、一件も引き継がれませんでした。

「切り替えたのだから、古い A レコードもそのまま新しい DNS に移るだろう」と考えていたら、ここで作業は止まっていたはずです。実際には、ゾーンを成立させるための NS と SOA は用意されたものの、設定したはずの A/MX/TXT は空でした。

レコード切替前切替後の Xserver Domain 側
NSns1.xserver.jp 〜 ns5.xserver.jpns1.xdomain.ne.jp 〜 ns3.xdomain.ne.jp （自動生成）
SOA—自動生成
A （ pyx.co.jp ）設定あり無し
A （ www.pyx.co.jp ）設定あり無し
MX設定あり無し
TXT （ SPF ）設定あり無し

紛らわしいことに、切り替え後の管理画面にも NS が 3 件と SOA が 1 件の 4 行が並んで見えました。しかしこれらはゾーン（レコードを収める器）を成立させるための構造的なレコードにすぎず、実際に使われる値 (A/CNAME/MX/TXT) は 0 件でした。
画面に行が見えていることと、設定が引き継がれていることは、同じではありません。

採った対応：ゾーンを空のまま進める

失われたレコードは復元せず、空のまま次の工程へ進む判断を採りました。理由は次の三点です。

  1. 控えていた値は、いずれ捨てるものだった。 A レコードの向き先は凍結予定の旧サーバーを指し、 MX はメール対象外だった
  2. 復元してから後の工程で消す、という往復を作らずに済む。変更する箇所が少ないほど、間違える箇所も少ない
  3. 結果として、後の DNS 切替（工程 5 ）が既存レコードの整理を伴う書き換えから純粋な追加に変わり、消し忘れによる証明書発行の失敗というリスクが構造的に消えた

ここで役に立ったのが、 3-1 で控えた値でした。
何が失われたのかが分からなければ、失って構わないかどうかも判断できません。控えを取っていたからこそ、これは捨ててよい値だと、根拠を持って判断できました。

この判断に伴う副作用として、 A レコードが存在しないため、キャッシュが切れ次第 pyx.co.jp は名前解決できなくなりました。二年間放置されたサイトだったため実害はないと判断しましたが、この影響は 3-4 で改めて触れます。

反映が安定するまでの経過

切り替え直後は、通常の調べ方（リゾルバ経由）で確認するたびに、結果が異なりました。

時刻照会先結果
12:13リゾルバwww と TXT が消失して見える
12:19リゾルバTXT が復活して見える
12:25リゾルバwww も復活して見える（＝旧ネームサーバーのキャッシュ）
12:35権威サーバー直撃ゾーンは空。以後この判定は一度も揺れなかった
翌日権威 3 台＋リゾルバ全て一致。 apex は応答 0 件、 www は該当ドメイン無し

もう一つ分かったこと。
ネームサーバーを切り替えた後も、旧ネームサーバー ns1.xserver.jp / ns2.xserver.jp などには、しばらく旧ゾーンが残っていました。そこへ直接問い合わせると、旧サーバーの IP アドレスを返します。
しかし、レジストリの委任先からはすでに外れているため、通常の名前解決でそこへ到達することはありません。「古い情報が残っている」ことと「古い情報が使われている」ことは別です。

原因は技術的な障害ではなく、誰に問い合わせているかでした。
通常の調べ方は途中のキャッシュを経由するため、変更直後は古い情報と新しい情報が混ざります。一方、そのドメインの設定を実際に保持している権威サーバーへ直接尋ねると、答えは最初から一貫していました。

調べ方分かることキャッシュの影響
権威サーバーへ直接
dig @ns1.xdomain.ne.jp …		設定の実態。ゾーンに何が書かれているか受けない。変更した直後から確認できる
通常の調べ方
dig …（ @ なし）		世間から見えている状態。浸透が完了したか受ける。変更直後は旧情報と新情報が混在する
設定を確かめたいときは、待つのではなく、聞く相手を変える。

これが、この移行を通じて得たいちばん実用的な教訓でした。設定が正しいかどうかは、変更した直後から権威サーバーに聞けば分かります。時間を置く必要はありません。
さらに紛らわしいのは、「レコードが存在しない」という否定の答えもキャッシュされることです（ネガティブキャッシュ）。設定した直後に通常の方法で調べると「まだ無い」と表示されるのが普通で、これが一時間ほど続くこともあります。ここで設定を疑って触り直すと、正しかったはずの設定を壊しかねません。

3-3. 工程 3 ：サイトを構築する

作業は AI に指示を出しながら進めました。新規リポジトリ pyx-site を作成し、準備中であることを示す一枚物のページを、プレビュー URL で確認できる状態にするまでが、この工程の範囲です。

項目内容
構成依存パッケージなしの単一 index.html （ CSS/JavaScript を内包）。ビルド工程は無し
表示内容PYX.CO.JP と Something new is taking flight. の一言。都会の空を表現したビジュアルの中を、矢印キーまたはマウスポインタで操作できるドローンが飛ぶ、インタラクティブな演出
対応端末PC でのキーボード・マウス操作を前提とし、スマートフォン幅での表示も別途確認

ページ全体を一枚の HTML ファイルに収めたのは、更新の対象を増やさないためです。凝った内容にするほど、後で「移す」／「保守する」対象が増えます。
まずは表示させることを優先し、内容は後からいくらでも作り込める形にしました。

GitHub Pages の設定は、リポジトリの Settings → Pages で、公開するブランチ（ main ）とフォルダ（ルート）を選ぶだけです。数分待つと、標準の github.io URL でサイトが公開されます。
この時点ではまだ独自ドメイン (Custom domain) を設定しません。設定すると標準 URL が独自ドメインへ転送されるようになり、動作確認に使えなくなるためです (2-5) 。

確認は、ローカル（手元のパソコン）と、 GitHub Pages のプレビュー URL の、二段階でおこないました。順番に確認することで、問題が起きたときに「ファイル自体の不具合」か「配信設定の不具合」かを切り分けやすくなります。

次の工程（旧環境の削除）に進んでよい条件
  • ☐ ローカルと GitHub Pages のプレビュー URL の両方で、ページが正しく表示される
  • ☐ 矢印キーでドローンが操作でき、加速・減速・画面端での挙動が意図どおり
  • ☐ マウスポインタでもドローンが操作でき、キー操作からの切り替えが自然
  • ☐ スマートフォン幅での表示を確認済み（レイアウトが崩れない、または操作不可である旨が破綻なく表示される）
  • ☐ 主要ブラウザ（ Chrome/Safari 等）で表示・動作を確認済み
  • ☐ タイトルなど、基本的なメタ情報が意図どおりになっている

次の工程で旧環境を削除すると、後戻りができなくなります (3-4) 。この確認だけが、削除に進む前の唯一の安全策になるため、満たしていない項目があれば、先を急がずここで直しました。

3-4. 工程 4 : 旧 WordPress 環境を削除する

3-3 の完成条件をすべて満たしたことを確認したうえで、サーバー内の WordPress のデータベースとファイル一式を削除しました。
削除するのは WordPress のデータのみで、サーバー契約自体の解約は行いません。契約は期限日まで通常どおり継続し、自動更新が設定されていないため、期限日に自然に凍結される見込みです。

この工程には、二つの影響がありました。

影響内容
ロールバック手段が失われる削除後は、 A レコードを旧サーバーへ戻しても、表示すべき中身がもう存在しない。空のページかエラーが表示されるだけになる
pyx.co.jp は既に無反応になっていた工程 2 でゾーンを空のまま進める判断を採ったため (3-2) 、 A レコードが存在せず、この工程を待たずに pyx.co.jp は既に名前解決できない状態にあった

当初は「削除から DNS 切替までの間だけ、表示が乱れる」と想定していましたが、実際にはその期間が前倒しで始まっていた形です。二年近く利用されていないサイトだったため実害はないと判断しましたが、削除の成否をブラウザで確認できなくなったため、確認手順はサーバーパネル経由に切り替えました。
後戻りが存在しない作業では、安全策は「事前の確認」に一本化されます。本計画では、削除より後でロールバックする方法を用意するのではなく、削除に進む前の完成確認 (3-3) に安全性のすべてを預ける設計にしました。

3-5. 工程 5 ： DNS を GitHub Pages へ向ける

まず GitHub 側で Custom domain を設定し、そのあとで DNS レコードを設定する。この順序を守りました (2-5) 。
GitHub 公式ドキュメントでは DNS プロバイダ側でドメインを向ける前に GitHub Pages 側へカスタムドメインを追加するよう明記しています。先に DNS だけを向けてしまうと、そのドメインで第三者が自分のサイトをホストできてしまう状態が生じうるためです。

リポジトリの Settings → Pages にある Custom domain 欄に pyx.co.jp を入力して保存すると、直下に DNS Check in progress と表示されます。この時点ではまだ DNS 側を設定していないため、確認は失敗表示のままですが、想定どおりで異常ではありません。
保存と同時に、リポジトリ直下に CNAME ファイル（中身は pyx.co.jp の一行のみ）が GitHub 側で自動生成・コミットされました。

続いて Xserver Domain 側の DNS レコード設定画面で、次の 5 件を追加しました。工程 2 でゾーンを空のまま進めていたため (3-2) 、これは削除・書き換えを伴わない、純粋な追加作業でした。

タイプホスト名値
A@ （ pyx.co.jp 自体）185.199.108.153
A@185.199.109.153
A@185.199.110.153
A@185.199.111.153
CNAMEwww（ GitHub のユーザー名） .github.io

GitHub Pages 向けの A レコード 4 件は、 GitHub の公式ドキュメントに記載されている固定値です。 www.pyx.co.jp でアクセスした場合も pyx.co.jp へ転送されるよう、あわせて CNAME レコードも設定しました（この CNAME の値にはリポジトリ名を含めません）。

反映確認は、ここでも二段階でおこないました。設定した直後に権威サーバーへ直接確認し、三台とも同じ答えを返すことを確認したうえで、時間を置いてから通常の調べ方で世間から見えるようになったかを確認しました。

# 設定が正しいか（権威サーバーへ直接、待つ必要なし）
dig @ns1.xdomain.ne.jp pyx.co.jp A
dig @ns2.xdomain.ne.jp pyx.co.jp A
dig @ns3.xdomain.ne.jp pyx.co.jp A
dig @ns1.xdomain.ne.jp www.pyx.co.jp CNAME

# 世間から見えるようになったか（時間を置いてから）
dig pyx.co.jp A
curl -I https://pyx.co.jp

権威サーバー側の答えが揃っていることを確認できたため、あとは時間の問題でした。 GitHub の Pages 設定画面が DNS Check successful （緑のチェックマーク）に変わったのを確認したあと、 Enforce HTTPS を有効化しました。
SSL 証明書の自動発行には最大 1 時間程度、反映には最大 24 時間程度かかることがあるとされていますが、今回は大きな遅れなく反映されました。

3-6. 工程 6 ：切替後の検証

最後に、独自ドメイン経由での表示を確認しました。

  • ☐ https://pyx.co.jp で新しいページが表示される
  • ☐ http://pyx.co.jp が https://pyx.co.jp へ自動転送される
  • ☐ https://www.pyx.co.jp が正しく転送・表示される
  • ☐ ブラウザで証明書エラーが出ない（ HTTPS が有効）
  • ☐ 独自ドメイン経由でも、キー操作・マウス操作が問題なく動作する
  • ☐ スマートフォンからのアクセスでも表示が破綻しない

ここまでで、当初の目的だった「サーバー契約期限までに、旧サイトの表示に依存しない形へ移行する」ことは達成できました。

確認事項状態
ネームサーバーの Xserver Domain への切替済み
旧 WordPress 環境の削除済み
GitHub Pages への DNS 切替・ HTTPS 化済み
ドメイン更新料の反映確認 (whois) 要確認

最後の一点だけ、この記事の執筆時点ではまだ確認できていません。
ドメインの登録有効期限は、支払いが済んでいても、レジストリへ実際に反映されるまでは古い期限のまま表示されることがあります。更新料は既に支払い済みですが、更新の反映が正しく行われたかどうかは、期限が明けたあとに、あらためて自分で確認するつもりです。
ここが失敗していると、ドメインそのものを失いかねません。移行作業の達成感とは別に、最後まで気を抜けない一点として記録しておきます。

ロールバックという選択肢はもうありません。工程 4 で WordPress のデータベースとファイルを削除したため、「 DNS を旧サーバーへ戻せば旧サイトが復活する」という形のロールバックはこの時点で、もはやできません。
今後もし独自ドメインの表示に問題が見つかった場合の対応は、旧サイトへの復元ではなく、以下のいずれかになります。

  1. ページの内容・動作を index.html ごと直接修正して push する
  2. 権威サーバーへの確認で「設定は正しいが未反映なだけ」かを切り分ける

終わってみると、この移行でいちばん難しかったのは、 DNS のコマンドを覚えることでも、 GitHub Pages を設定することでもありませんでした。
「いま何が、どの契約に紐づいているのか」を見誤らないこと。そして「ここから先は戻れない」という地点を、先に見つけておくこと。
緊張が集まっていたのは、この二点でした。

4-1. 「待つ」より先に、「誰に聞くか」を考える

  • サーバー契約をやめる前に、 DNS の管理と名前解決がどの契約に紐づいているかを確認する。憶測で進めず、事業者に直接問い合わせる (2-2)
  • DNS に触る前に、現在の設定を全件控える。使わないと分かっていても、「何を失うかを知る」ためだけに価値がある (3-1)
  • ネームサーバーを切り替えても、既存のレコードが引き継がれるとは限らない。画面に行が見えることと、設定が引き継がれていることは別 (3-2)
  • 設定を確かめたいときは、待つのではなく、聞く相手を変える。権威サーバーに直接聞けば、変更した直後から答えが分かる (3-2)
  • 後戻りが存在しない工程（今回で言えば旧環境の削除）の前には、安全策を「事前の完成確認」に一本化する (3-3 / 3-4)
  • Custom domain の設定は DNS レコードの設定より先に行う。順序には、思いつきではなく理由がある (2-5 / 3-5)

4-2. 移行で得たものは、費用よりも単純さだった

費用の面では、月々のレンタルサーバー代が無くなり、かかるのはドメインの維持費用だけになりました。これは移行の目的そのものではなく、動いていないサイトから動的な仕組みを取り除いた結果として、後からついてきた副次的な効果です。

ドメインの管理アカウント、 GitHub のアカウント、それらのパスワードの管理は引き続き必要です。静的サイトはページを配信する部分の攻撃対象を大幅に減らしますが、「公開する権限を持つアカウントを守る」という仕事は残ります。
ただしこれは、プラグインを毎月更新し続けるより、ずっと単純な仕事です。

4-3. 移行後に残ったもの、消えたもの

移行を終えて実感するのは、サイト維持のためにおこなう作業の少なさです。 WordPress の管理画面・ PHP ・データベース・プラグイン更新・サーバー側の保守という一式を抱える必要がなくなり、サイトを更新するときは、基本的に HTML ファイルを更新したら Git 操作で commit ～ push するだけで済む様になりました。
もちろん GitHub や、ドメイン管理のアカウントを守るタスクは残ります。それでも、格段にシンプルな流れになったことは確かです。

pyx.co.jp は、二年間、必要もなく動的サイトであり続けました。今回の移行は、その状態に区切りをつける作業でもありました。

結局、移したのはサイトというより、サイトを支える仕組みでした。動的な仕組みを外し、 DNS の役割を整理し、最後に残ったのは、必要なときに HTML を更新して GitHub へ push するという、ずっと小さな運用です。
